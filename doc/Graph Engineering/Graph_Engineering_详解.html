ENGINEERING FIELD GUIDE / 2026.09

Graph Engineering把工作画成依赖图，把结论接到证据上。

并行能缩短独立工作的等待；契约、完整性检查与外部证据决定结果是否值得使用。图的价值来自正确拆分与可验证执行，不能仅靠增加 agent 数量获得。

01

图描述工作，也暴露等待

节点负责有边界的任务，边表达任务之间的依赖。画图的第一步，是说清楚“谁必须等谁，以及为什么”。

从单个循环到协作流程

Graph Engineering 可以组织多个工作与检查循环。它沿用图、依赖调度和工作流思想；本文将其当作工程设计方法，而非新的标准或算法。

教学补充节点可以是模型、脚本、编译器或人工审批。结构化输出可以包含多个产物引用。

直线也是图。DAG 是无环依赖图；图可含回路；带修复回边的局部循环必须有次数、时间或预算上限。不要把所有图都当成 DAG。

Node · 做什么

任务、输入、输出、边界、完成判据。

Edge · 为什么等

产物依赖、控制条件，或需要显式管理的资源约束。

State · 到了哪里

状态、尝试次数、产物、证据和版本。

02

Node contract：让下游不用猜

固定任务范围与输出结构，才能把一个节点可靠地接到下一个节点。

契约最小字段

字段要约束的事情
job / input做一件事；输入显式传入。
output / schema状态、发现列表、证据引用、版本可解析。
acceptance可执行通过判据；空发现不等于执行失败。
limits / effects超时、预算、重试次数、可写范围和资源锁。

教学补充自由文本可保留在说明字段中；路由与验收字段应有机器可检查的结构。

{
  "schema_version": "1.0", "run_id": "demo-run", "node_id": "isr-audit",
  "snapshot_id": "<git commit + config hash>",
  "status": "succeeded", "findings": [],
  "evidence": [{"kind": "analysis", "artifact": "<report path>"}],
  "coverage": {"expected_files": 8, "checked_files": 8}, "attempt": 1
}

教学示例数据，不是实际测试结果。findings=[] 仅说明该检查在声明范围内未发现问题，不能证明整套系统无缺陷。

03

真假依赖：先找输入，再查资源

问：B 是否真的要用 A 的结果？如果不用，顺序可能只是提示词的书写顺序。

删除假边的检查顺序

  1. 列出 B 读取的输入，确认是否来自 A。
  2. 列出双方写入的文件、设备与外部状态。
  3. 确认公共快照不可变，产物路径不碰撞。
  4. 确定可用并发和汇合规则，再并行执行。

保留必要同步

教学补充资源冲突可用锁、队列或隔离管理，不必把所有工作永久串成一条链。

独立 worktree 隔离文件修改；合并仍可能出现文本与语义冲突。跨模块接口与全量构建需要另行验证。

04

Diamond：分开探索，带证据汇合

Fan-out → Reduce → Verify → Synthesize：让任务并行，让代码整理结果，让独立检查先于最终报告。

每层只做擅长的事情

Fan-out：按范围或角度分工，覆盖可追踪。分得更宽提升覆盖机会，不自动改善判断。

Reduce：先检查任务结果，再用代码去重、排序、限制体积。仅按 URL 去重可能误删同页不同发现；宜使用发现 ID 与证据定位。

Verify：只给结论、必要材料和独立取证入口，避免复用生成者整段对话。

Synthesize：汇总证据与分歧，不把报告的流畅程度当作通过条件。

独立上下文不等于独立证据。
相同模型和来源仍可能产生相关错误。关键结论需要真实测试、原始材料或人工复核。

教学补充多个验证者可以采用多数投票。工程关键验收项应逐项通过；不能用两票赞同抵消一个实测失败。

05

状态、失败与有限重试

教学补充“没有返回”不是状态。为每个任务保留结果信封，即使它失败、超时或被取消。

按失败性质处理

  • 超时 / 限流：有上限的退避重试，遵守服务端等待建议。
  • 格式错误：返回具体校验信息，可限次修正。
  • 权限不足 / 版本错误：先修复前置条件。
  • 实测断言失败：进入有边界的修复循环，保留失败证据。
// 教学伪代码：描述处理顺序，不是某个 SDK 的可执行 API。
// 输入：任务结果 result、当前尝试次数 attempt、固定版本 snapshot。
// 运行时负责超时、预算扣减和持久化；超时也要生成结果记录。
max_attempts = 2  // 总尝试上限：首次执行 + 最多 1 次重试

on_result(result):  // 每次尝试结束时处理成功、失败或超时结果
  // 先保存结果、尝试次数和输入版本，方便追踪与断点恢复。
  persist(result, attempt, snapshot)

  // accepted 检查执行状态、输出结构及验收条件，不能只听模型说完成。
  if accepted(result):
    mark_succeeded()  // 标记节点成功，供下游检查启动条件

  // 可恢复的瞬态错误、剩余尝试次数和剩余预算，三个条件必须同时满足。
  else if transient(result)
       and attempt < max_attempts
       and budget_remaining:
    wait(backoff_with_jitter)  // 退避并加入随机延迟，避免集中重试
    // 同一逻辑操作复用幂等键，防止重复副作用。
    // 重试函数须增加 attempt，并在执行前再次核对预算和远端状态。
    retry_with_same_idempotency_key()

  else:
    mark_terminal_failure()       // 保存终态失败及原因，不再自动重试
    block_required_dependents()  // 阻断必须依赖该结果的下游节点
// 输出：持久化的任务状态；失败不能冒充“成功但没有发现”。
超时不意味着远端操作已停止。烧录、写库等副作用需要状态核对与幂等机制；重试不能简单再次发送同一操作。
06

三大故障：并行成功也可能是假象

上下文坍缩、虚假独立、静默失败，是扩大图规模时最容易暴露的三个问题。

01 上下文坍缩

原始结果挤进一个综合节点，输入超限或关键细节丢失。

处理：分批归并；摘要保留证据 ID 与原始产物引用，压缩后仍可回查。

02 虚假独立

任务不同，却改同一个文件、占同一块板或争 API 配额。

处理：隔离工作区、资源锁与限流；汇合后做集成验证。

03 静默失败

过滤空值后直接汇总，少做一项也能产出“完整报告”。

处理：核对预期 ID 集合、状态、版本与覆盖，不只比较长度。

互动 A · 让一个分支出问题

模拟三个必需节点 A / B / C。选择情形，观察 fan-in 是否允许生成完整报告。按钮支持 Tab 与 Enter / 空格。

允许综合：A、B、C 均已成功，ID 唯一且快照一致。
expected = [A, B, C]
received = [A, B, C]
missing = [] · duplicates = [] · invalid = []

这里采用严格策略：必需节点缺失或不合格均阻断综合。可选分支可允许降级，但必须在契约中预先声明，并在报告显著标出缺口。

// 教学伪代码：先验收任务结果，再对结果中的“发现”去重。
// 输入：计划任务 ID 清单，以及各任务返回的结果信封。
expected = set(planned_node_ids)  // 本轮应该收到哪些任务的结果

// 收集成功、失败和超时结果，并保留 node_id，不过滤失败记录。
// 运行时须设置截止时间，避免一个不结束的任务阻塞整个汇合。
received = all_settled_results_with_node_ids()

// 同一 ID 重复返回不能顶替缺失任务；未知 ID 也不能混入当前运行。
// reject 表示门禁不通过：登记原因并停止生成“完整报告”。
reject duplicate_ids(received), unknown_ids(received)

// 集合差集找出缺失 ID：例如预期 {A,B,C}、收到 {A,B}，缺失为 {C}。
reject expected - set(received.ids)

// 每个必需结果都必须通过下列检查；可选节点的降级规则需另行声明。
require every required result:
  status == succeeded AND schema_valid  // 执行成功，字段和类型符合契约
  AND snapshot_id == current_snapshot   // 结果属于当前代码与配置版本
  AND coverage_complete                 // 声明的检查范围没有漏项

// 输出：允许汇合，或带具体缺口的失败状态。
// 全部通过后才归并 findings；零发现也必须保留成功信封。
// 这里的门禁检查完整性，发现是否真实仍需后续独立验证。
07

Anchors：让结论落在可追溯证据上

多个节点彼此认可，可能只是重复同一个错误。拓扑本身不能证明结论为真。

可执行的锚点是什么

实际运行：测试命令、退出码、原始日志、运行时间、构建 ID，能够一起定位到一次执行。

原始来源：结论对应到文档版本、日志行、波形区间或可复现输入。

固定门槛：运行前约定的功能断言、时间限制与失败处理，不在修复过程中悄悄降低。

教学补充锚点也有适用范围。测试通过只覆盖本次配置、输入与观测能力；陈旧固件、错误仪器设置或不充分用例仍会产生误导。

证据至少关联 run_id → commit → config → toolchain → board → artifact。不要把不同版本的通过记录拼成当前版本“全部通过”。

08

何时不用：简单路径也很专业

任务小、步骤真正串行、目标仍在探索，或每步都必须人工确认时，复杂编排可能只增加开销。

几类常见选择

一个难复现的板级 bug：先补现象、复现条件和观测，使用可随时调整的调查循环。

几十个模块同规则审查：适合分片只读分析，随后检查跨模块关系。

一块板上顺序烧录与测量：设备阶段串行；旁路静态分析仍可并行。

逐步审批的敏感变更：在自然里程碑设置门禁，收益按实际等待重新计算。

从能解决问题的最简单方案开始，再按需要增加复杂度。

09

算时间，也算完整执行的成本

教学补充图的总耗时受关键路径与资源限制。只有一层完全独立任务、资源足够且忽略开销时，才能直接取最慢任务时间。

关键路径 L = max（每条依赖路径上节点耗时之和）
理想调度下界 T ≥ max(L, W / C)
W = 所有节点的工作量；C = 同质执行资源数。此下界不保证可达到。

互动 B · 串行与并行，究竟差多少？

模型：准备 P → 三个独立任务 A / B / C → 独立验证 V → 综合 S。拖动任务耗时、并发上限与额外编排开销。

串行基线105 s
当前并行调度70 s
加速比 / 串行 ÷ 并行1.50×
任务执行额外编排开销 H准备 / 验证 / 综合

默认并发为 3：A、B、C 同时开始；分支阶段耗时 40 秒。

P=5，V+S=10 秒；串行 5+20+30+40+10=105 秒；理想无限并发 55 秒，增加 H=15 后为 70 秒。

模拟器假设与适用范围

  • P=5、V=4、S=6 秒固定（V+S 对应 PPT 的汇总 10 秒）；两方案做同样任务与验证。
  • A/B/C 耗时固定，互不依赖，不可抢占；执行槽同质。
  • 按 A→B→C 入队，把下一项分给最早空闲槽；这是可复现调度，不保证最优。
  • H 仅为图方案额外的一次串行开销，放在准备后；共同开销已包含在各任务时间中。
  • 无失败、限流、缓存与 I/O 争用；独立验证 V 是一个全量检查节点。

如何读关键路径

本例原始依赖图的 L=15+max(A,B,C)。当 C=3，任务都能启动，理想图耗时为 L+H。

C<3 时，有些独立任务被资源迫使排队；实际耗时是 15+H+分支调度长度。不要把资源等待误称为原有数据依赖。

多层图应计算完整依赖路径；只有显式层间屏障时，才可逐层取最大值后相加。

Token 与工程成本是另一张账

成本项为何发生控制方式
模型输入 / 输出每个 worker、verifier、synthesizer 都会消费 token。按节点统计实际用量；控制输入与输出上限。
上下文传递脚本变量可以避免主会话反复接收中间结果；下游模型阅读材料仍需输入 token。结构化摘取、引用原始产物、合理缓存。
重试与重复验证失败会增加尝试次数、工具调用与等待。attempt、时间、token、总任务数多重硬上限。
工程与设备编排、日志、存储、设备占用、集成和人工审查。先跑少量任务，比较总费用与已验证结果。
代码中的去重与排序本身不调用模型；它们仍消耗计算资源。不能据此推导“结果传递零 token”或“整个协调过程免费”。
10

嵌入式 / FreeRTOS：并行调查，串行占板

教学补充 · 假设案例假设要调查“高负载下偶发丢帧”。以下是工作流设计示例，没有对应真实板卡、日志或已确认根因。

先界定现象

补齐负载、输入速率、丢帧判据、触发概率与固件版本。没有这些信息时，先做观测方案，不能让多个节点放大猜测。

再形成可证伪怀疑点

A 检查中断上下文中的 API 使用与项目移植约束；B 检查生产消费路径、返回值处理与缓冲区生命周期；C 对齐丢帧与时序证据。

以上都是检查方向，不是已确认的 FreeRTOS 缺陷或该项目根因。具体约束以项目 FreeRTOS 版本、port 与配置为准。

最后执行验证

独立检查者读取源码位置、候选变更和原始数据，提出能推翻假设的实验。由单一集成者形成一致构建后执行基线与候选对照。

设备任务记录板号、二进制哈希、配置、采集设置与原始日志。测试未执行时，报告写“待验证”；阈值必须来自项目验收要求。

编排图不是 RTOS 调度图。
这里的节点是开发与验证工作，不是固件 task。它不能证明固件满足实时截止时间、ISR 延迟或并发安全要求。
// 教学调用树：缩进表示包含关系，同级步骤默认依次执行。
// parallel_read_only 内的三个分支可并行，结束后才进入汇合检查。
// 输入：待调查现象、代码与配置、已有日志和冻结的验收条件。
run_investigation
  freeze_inputs  // 固定 commit、配置和日志快照，避免分支分析不同版本

  parallel_read_only  // 只读共享输入，各分支写入独立产物目录
    audit_isr_calls                 // 检查 ISR 调用边界与项目约束
    inspect_queue_and_buffer_paths  // 检查队列、缓冲区所有权和错误路径
    correlate_existing_logs         // 对齐已有日志与时序，形成待验证线索

  check_fan_in_integrity  // 核对分支 ID、状态、版本和覆盖，缺项不得放行
  independent_verify_hypotheses  // 新上下文复核假设，回查原始证据
  produce_patch_candidate       // 依据复核结果形成候选补丁，标出未验证项
  integrate_and_build           // 单一集成者合并变更，构建一致固件

  acquire_board_lock  // 独占目标板卡，避免另一任务同时烧录或复位
    flash_exact_artifact    // 烧录本次构建产物，记录二进制哈希
    run_frozen_test_plan    // 按预先确定的条件测试，不为过关放宽阈值
    save_raw_measurements  // 保存原始日志、测量值、板号与时间
  release_board_lock_in_finally  // 无论成功或异常，都在安全收束后释放锁

  write_report_with_evidence  // 输出结论、证据、覆盖情况和待验证项
  human_gate                 // 展示候选变更与风险，批准后方可合入或发布
// 前置步骤失败时，停止依赖它的后续操作，登记缺口并输出诊断报告。
// 输出：可追溯的调查报告和候选变更，不把未运行测试写成已通过。

可复制的框架无关 Graph Spec

教学补充先把契约、资源与验收写清楚，再映射到脚本、任务队列或 agent 框架。下面是设计规格，不是某个运行时的可直接执行 API。

Graph Spec · 嵌入式调查模板

把尖括号占位符替换为项目参数；数值上限是教学起点，执行前按预算调整。



映射到框架时检查什么
运行时需要实现调度、状态持久化、超时、资源锁与预算。自然语言中的“硬上限”不会自动变成执行限制。
LangGraph 支持工作流、并行与 orchestrator-worker 等模式，并区分预定代码路径和 agent 动态决策。上面的 Spec 不是 LangGraph API。
Claude Code 产品特定入口
Dynamic workflows 由 JavaScript 脚本编排 subagents，中间结果保留在 script variables。
可明确请求 Create a workflow。也可以通过 ultracode 入口使用。
产品入口随版本变化：v2.1.160 之前的字面触发词是 workflow，当前介绍 ultracode 与自然语言请求。入口受版本、配置、输入渠道和组织设置影响，不保证所有配置都可用，也不是跨框架通用指令。

使用边界


模拟参数与嵌入式案例用于解释工作流设计，实际效果需要在项目中验证。


示例与实测
模拟秒数不是实际测量结果，嵌入式案例不代表已执行固件或板级测试。伪代码与 Graph Spec 需要映射到实际运行时。

SMALLER CHANGES. CLEARER INTENT.

让 AI 少造轮子，
把项目做得更简单。

Ponytail 给编程助手一套选择方案的规则：先理解需求和现有代码，再寻找满足要求的简单实现。本指南从“装在哪里”讲到“在项目中怎么说、怎么检查”。

开始接入 ↗ 复制项目提示词
它在开发流程中的位置
你的需求 + 项目代码↓编程助手读取 Ponytail 规则↓优先复用，减少多余实现↓修改代码 → 验证行为
01 /

它解决什么问题？

LESS DUPLICATION

已有能力，先找再写

项目已经有函数、工具或成熟模式，就先复用。避免为了同一件事再写第二套代码。

LESS SPECULATION

当前不需要，先不建

不因为“以后可能用到”就添加配置层、工厂、框架或新依赖。

SMALLER DIFF

用够用的改动交付

缩小改动范围，同时保留明确需求、必要错误处理和可运行的验证。

它的核心决策顺序可以这样理解：每向下一步，都先确认前面的办法是否已经够用。

这项能力现在真的需要吗？
项目里是否已经有可复用实现？
标准库能完成吗？
平台原生功能能完成吗？
已安装的依赖能完成吗？
能否用直接、简短的表达完成？
最后才补充必要的新实现。

“代码少”是选择方案后的结果。复杂度、边界条件与可读性仍要检查；不能为了少写几行删掉校验、丢失错误处理或省略真实硬件需要的校准能力。

依据：项目通用规则、主技能。

02 /

装在助手里，再用于你的项目

通常无需把 Ponytail 链接进业务程序、固件或构建系统。先选择助手的接入方式，再让助手在目标项目目录中工作。

当前环境优先阅读此项
1. 在终端检查前置条件

准备可用的 Codex CLI、Node.js 和访问 GitHub 的网络。hook 执行环境也需要能找到 node。

codex --version
node --version
2. 添加来源并安装插件

这两行是终端命令。它们安装到助手的插件环境，不需要放进项目的 package.json。

codex plugin marketplace add DietrichGebert/ponytail
codex plugin add ponytail@ponytail
3. 查看 hook 并重新打开任务

运行 codex，在交互界面输入 /hooks，查看实际列出的脚本并按界面流程信任。桌面版按仓库说明重启，然后在目标项目创建新任务。

4. 明确调用，再做小任务

在 Codex 中用 @ 查找技能；仓库采用下面的写法。优先从界面候选中选择对应技能，若显示带命名空间的名称，以实际候选为准。

@ponytail lite

先读取本项目的 AGENTS.md 和相关代码。
这次只调整指定功能，优先复用已有实现。
请先指出可复用位置，再执行最小必要改动。

切换模式建议单独发送一条消息，再发送具体工作请求。

本机已核对：Codex CLI 0.153.4 支持上述 marketplace add / plugin add 命令。本页没有执行安装，也没有完成安装后的 hook 运行验证。

只把简化原则用于当前项目

如果只想给一个项目加入写码约定，可以参考仓库的 AGENTS.md，将相关规则合并进现有项目规则。保留项目已有的构建、测试、硬件和安全要求。

your-project/
├── AGENTS.md       ← 加入一节约定
├── src/
└── tests/

路径仅示意。对于支持 AGENTS.md 的助手，它属于项目上下文；规则文件自身没有插件的模式状态、命令注册或 hook。

## 实现方式约定（参考 Ponytail）
- 先读相关代码与调用位置，再决定修改方案。
- 优先复用本项目函数、标准库和平台已有能力。
- 不为尚未确认的需求新增抽象层或依赖。
- 保留输入校验、错误处理和项目要求的测试。
- 硬件校准、时序和资源限制按项目约束执行。
- 说明本次简化的适用范围及再次扩展的条件。

以上为本指南建议的精简约定，不是官方文件的完整副本。若选择规则方式，停用时应调整该节规则；插件的 off 不会删除已经写入 AGENTS.md 的项目要求。

Claude Code 对话框内执行

按仓库说明，下面两条安装命令要分两次发送。不是放进 PowerShell 执行。

/plugin marketplace add DietrichGebert/ponytail

/plugin install ponytail@ponytail

安装后开始新会话，使用 /ponytail lite、/ponytail-review 等 slash 形式。与 Codex 的技能入口区分开。

其他助手有各自适配方式。使用 Cursor、OpenCode 等环境时，请查阅仓库对应章节，不直接套用 Codex 安装命令。

安装来源：README · Install。实际 hook 清单见配置文件：核查时包含 SessionStart、SubagentStart、UserPromptSubmit 三类事件；README 的“两项 hook”描述未完全同步。

03 /

第一次接触，先用 lite 比较方案

lite 是本指南给新用户的试用建议；插件缺省配置是 full。点击模式，观察同一个需求的处理倾向。

教学需求：为内部页面增加日期输入

Codex 消息：

这是对行为倾向的示意，不是实时模型结果。任何模式都应满足明确需求；例如业务确需范围选择、统一格式或特殊交互，就不能只用原生输入代替交付。

当前会话与下次默认值

显式发送 @ponytail full 切换当前模式；@ponytail off 停用。需要从 off 恢复时也明确写 lite 或 full。无参数 @ponytail 在当前 tracker 中用于报告状态，别把它当成必定重新开启。

希望新会话默认 lite？

在 Windows 的 %APPDATA%\ponytail\config.json 中合并下方字段；若文件已有其他设置，保留它们。

{ "defaultMode": "lite" }

读取优先级：环境变量 PONYTAIL_DEFAULT_MODE → 配置文件 → full。修改默认值后，开启新会话验证。

模式说明：主技能；配置：help；无参数行为与模式识别：mode tracker。help 部分措辞与实现有差异，此处按当前 tracker 区分状态查询和显式启用。

04 /

六个技能，按任务选择

下表采用仓库记录的 Codex @ 形式。Claude Code 对应使用 / 形式。技能由支持它们的宿主加载，不能仅靠把名字写进普通终端来运行。

Codex 调用什么时候用会得到什么／范围
@ponytail full开发、修复、重构前约束后续实现方式；是否修改代码取决于具体任务。
@ponytail-review提交前查看当前 diff列出可减少的复杂度及替代方式；只报告，不自动修复。
@ponytail-audit初次了解仓库的冗余扫描整个仓库并排序建议；只报告。大项目可先请求限定模块。
@ponytail-debt回顾有意留下的简化汇总代码中 ponytail: 注释；需要保存台账时显式指定文件。
@ponytail-gain了解作者的实验结果展示已有 benchmark 数据；不会测量你的项目节省了多少。
@ponytail-help忘记命令或配置方法一次性帮助卡，不应改变模式。

审查分工：review / audit 主要寻找多余封装、重复实现和不必要依赖；正确性、安全与性能需要正常代码审查及测试继续覆盖。

逐项来源：review · audit · debt · gain · help。

05 /

在一个真实项目中，按这四步使用

下面是可直接采用的团队实践建议。先从一个小功能试用，观察是否真的减少重复实现和维护成本。

STEP 01

给上下文

打开目标项目。指出需求、相关文件、必须保留的行为和已有构建／测试命令。

STEP 02

让助手找复用点

选择 lite 或 full。先读实现与调用处，再决定是否新增代码、依赖或抽象。

STEP 03

实施并检查

检查 diff，运行项目规定的验证；同时确认边界条件没有因简化而改变。

STEP 04

审查与记录

用 review 看过度设计，再做正常审查。对有实际限制的简化记录升级条件。

使用 ponytail skill，以 lite 模式处理下面的项目任务。

目标：为现有日志工具增加按关键词过滤的功能。
上下文：请先查找并读取现有日志解析、过滤函数及其调用处。
约束：保持现有输入输出格式；不新增运行时依赖。
执行：复用已有能力，只修改本功能相关文件。
验证：执行项目规定的测试，补充必要的边界检查。
交付：说明改动、复用位置、验证结果及尚未验证的部分。

自然语言适合表达工作要求；如果你依赖插件的持久模式状态，请先单独发送显式的 @ponytail lite。仅要求一句“按 lite 工作”不等于已验证 hook 状态发生变化。

    常见问题
    安装命令提示不支持？
    先运行 codex --version 和 codex plugin --help。确认正在使用的 CLI 支持插件命令；不同助手的命令不能混用。网络连不上 GitHub 时先解决连接问题。
    装好了，却没有自动生效？
    检查插件是否启用、hook 是否受信任、node 是否在 hook 的 PATH 中。重启桌面应用并新开任务，再显式选择 ponytail 技能。只复制 AGENTS.md 的方式不会提供自动模式跟踪。
    review 之后为什么没修改？
    review 和 audit 的定义是报告建议。选定建议后，继续要求助手实施，并明确保留行为和验证范围。
    gain 能算出本项目省了多少吗？
    不能。它展示作者已有实验；核查时 gain 技能仍写着旧的单次生成数据，而 README 已改用代理执行任务的基准。不能把任一数字视为本项目收益或安全保证。
    怎么停止，或移除？
    当前模式可显式发 @ponytail off；下次启动默认关闭可设置 defaultMode 为 off。卸载 Codex 插件使用 codex plugin remove ponytail。仓库另有清理脚本处理残留状态，执行前查看其范围；项目中自行合并的规则需单独调整。
    核查参考：启动脚本、gain 定义、卸载说明。

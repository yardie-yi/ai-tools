Loop Engineering
任务执行与验证

AI 按目标执行任务，通过测试或其他检查判断任务是否完成。检查未通过时，根据失败原因继续修改；达到资源上限或无法继续时停止。Loop Engineering 负责设计这套执行、检查和停止规则。

定义任务→执行与检查→保存状态→继续或停止
验收要求 哪些检查通过后，任务才能完成？示例任务 UART 流式协议解析器运行模拟 四种预设停止结果
01

概念与相关术语

一次请求通常返回一份回答或代码。闭环程序检查结果是否满足要求，再决定继续修改、结束任务或转交人工。Loop Engineering 是设计这套流程的方法，不限定具体模型或工具。

层次主要设计对象UART 解析器示例
Prompt Engineering设计单次请求中的任务说明、限制条件和输出格式“补齐分片输入逻辑，并解释变更。”
Context Engineering选择模型本次推理需要读取的规格、代码与日志提供帧规格、现有代码、失败样例与上一轮结论。
Harness Engineering设计 Agent 的运行环境（Harness）。Agent 指能调用工具执行任务的 AI 程序工作区、工具接口、测试执行、超时、权限与日志。
Loop Engineering根据检查结果安排下一轮工作，并定义停止条件修改代码 → 跑固定测试 → 读取结果 → 继续修改或停止。
Graph / WorkflowGraph / Workflow 用图表示任务之间的依赖、分支和执行顺序构建后分支跑静态检查与协议测试；图中可包含循环。
这些设计方法可以同时使用。Graph 描述任务之间的连接关系，Loop 规定检查结果如何影响下一步。流程图中即使有循环，也需要明确检查什么，以及何时继续或停止。

人工决定每次请求

人提问→AI 回答→人判断

适合一次性、小规模、以主观判断为主的任务。由人决定下一次输入。

CLOSED LOOP

控制程序根据检查结果安排下一轮

AI 修改代码→验证器→继续 / 停止

人先确定目标、允许的操作和验收范围；系统按这些要求执行。遇到异常或缺少必要检查结果时，转交人工。

02

闭环的五个步骤

每轮包含发现、计划、执行、验证和反馈五个步骤。验证未通过时，记录失败原因，下一轮针对这些原因修改。点击阶段可查看具体动作；发现阶段首次收集完整信息，后续更新变化和失败记录，每一步不一定需要调用模型。

DISCOVER / 收集信息

确认问题、复现条件与任务范围

收集规格、代码版本、失败用例、日志与环境状态。确认故障来自产品代码、测试代码还是工具。缺少关键协议约定时，标记为待确认并停止相关修改。

当前案例
输入：固定帧规格、解析器代码与跨两次接收的失败样例。
发现的问题：第二次输入到来前，解析器错误丢弃了尚未接收完整的帧；该问题可以复现。
下一步需要：复现方法、失败记录和验收范围
VERIFY

按既定要求判断是否完成

运行规格要求的测试、静态检查和必要的外部测量。模型自评分仅用于辅助定位问题，不能替代这些检查。

STATE

保存每轮操作和检查结果

保存已尝试的修改、代码差异、失败用例和下一步。重启后读取这些记录，避免重复无效修改。

STOP

定义未完成时的停止条件

检查通过时结束任务；预算不足、超时、轮数用尽、连续无进展或无法处理的故障，也必须停止并说明原因。

闭环系统的五个组成部分

下面五类功能常用于完整的自动化系统。最小实现可先包含执行任务的程序、运行检查的程序，以及负责保存状态和决定下一步的控制程序。

01

通过手动操作、事件或定时规则启动任务；防止重复启动和冲突任务同时运行。

执行 / 审查角色

执行者修改代码，审查者检查遗漏。可用多个 Agent 分工，也可先用一个 Agent。

由不同角色执行和检查
04

工具 / 连接器

读写工作区、运行构建、查询工单与调用设备；限制范围并记录操作。

执行文件、工具和设备操作
05

验证器

按事先确定的规则检查代码或文件，返回通过、失败或无法完成检查。

判断修改是否符合要求
定时启动和反馈闭环是两项不同功能。定时规则决定何时执行任务；反馈闭环根据上次检查结果和保存的状态决定本次做什么。只重复同一条指令不一定构成反馈闭环，独立审查也不能替代外部测试。
04

验证方法与适用范围

执行前先确定验收条件。每份报告记录被检查的代码版本，不同方法分别检查不同问题。测试通过只能说明本次测试覆盖的内容符合要求。

检查方法能证明什么不能单独证明什么
模型自检 / 评分回答或代码是否明显偏离要求，是否存在可疑逻辑。实际运行是否正确、安全，或满足时序要求。模型评分高不能作为通过依据。
独立审查另一个角色按检查表寻找遗漏、边界和不一致。两个模型意见一致仍可能共同出错。
机器可执行检查构建、静态规则、固定用例、属性测试在声明环境下的结果。未测输入、实板电气行为、长期稳定性。
外部系统 / 硬件测量指定固件、板卡和测量条件下，实际运行满足明确要求。不同硬件版本或未覆盖环境同样正确。
FIXED ACCEPTANCE RULES

执行时不得自行修改原定验收标准

  • 执行前确定验收规格与关键测试的版本。
  • 执行者不能自行删用例、跳过检查或降低阈值。
  • 发现规格或测试有误，单独提出修改并重新确认验收。
  • 保留执行者未见过的测试或独立回归用例，检查修改能否处理其他输入。
REPORT AND CODE VERSION

检查报告必须对应本次代码

  • 代码内容哈希（用于识别内容是否变化）或提交标识。
  • 规格哈希、测试集哈希与验证器版本。
  • 构建环境、工具链和设备标识（如适用）。
  • 检查命令、退出码、日志或报告位置及时间。
检查返回 PASS（通过）、FAIL（失败）或 UNKNOWN（无法确认）。检查未执行、工具超时、设备断开，或报告对应的代码版本不同，都应标记为 UNKNOWN。只有必需检查明确返回通过，才能标记任务完成。
05

持久状态与停止条件

把任务状态写入文件或数据库后，程序重启时可以继续处理。保存状态不会训练模型，也不会改变模型参数。每轮向模型提供必要摘要，定位问题时再读取详细日志。

CHECKPOINT

状态文件需要保存的信息

STOP POLICY

不同停止状态的触发条件

状态触发条件
ACCEPTED当前代码版本的全部必需检查通过。
LIMIT_REACHED调用前预算不足，或达到总时限/轮数。
NO_PROGRESS连续规定轮数内，失败用例没有减少。
NEEDS_HUMAN缺少必要规格、设备不可用、操作超出允许范围或故障无法恢复。

提前定义“有效进展”，例如在同一测试集下，失败用例减少且没有新增失败。模型评分上升、回答变长或重复应用同一修改，均不能代替检查结果。

写状态时采用同目录临时文件 → 同步写入存储 → 原子替换。原子替换指新文件完整写入后一次替换旧文件，避免只覆盖一部分。每轮保存，停止前再保存一次；恢复时核对代码和报告版本，不一致就重新检查。外部写入采用幂等键，即用唯一操作编号识别重复请求，避免重复提交。重复执行不保证任务最终完成，因此必须设置无进展和资源上限等停止条件。

# 先确定目标与验收要求；执行者不可自行修改规格、检查规则和受保护测试
spec = load_locked_spec()
state = load_or_create_checkpoint(spec.task_id)

try:
    assert_resume_compatible(state, spec)  # 核对规格和工作区版本；不一致时转交人工
    while state.round < spec.max_rounds:
        check_total_deadline()  # 使用持久化任务起始时间，恢复后不重置
        state.round += 1
        atomic_checkpoint(state)  # 调用前保存轮数，程序崩溃恢复后仍计入已用轮数

        # DISCOVER：读取必要的规格、代码和日志；缺少关键协议约定时停止
        context = collect_context(spec, state, bounded_call)
        if context.has_blocking_unknown:
            stop("NEEDS_HUMAN", context.unknowns)

        # PLAN：根据失败用例和已试方法，选择本轮要修改的一个问题
        plan = bounded_call(planner, context, spec.plan_budget_cap)
        enforce_scope(plan, spec.allowed_paths, spec.allowed_actions)

        # EXECUTE：所有模型、工具和子代理调用都必须检查预算并设置超时
        candidate = bounded_call(executor, plan, spec.execute_budget_cap)
        candidate_id = snapshot_hash(candidate)  # 保存该版本的代码标识，验证期间禁止修改

        # VERIFY：在固定测试与环境中检查；超时/跳过/缺日志都不是通过
        evidence = bounded_call(verifier,
            (candidate_id, spec.locked_acceptance), spec.verify_budget_cap)
        state.evidence_ref = save_evidence(evidence)
        state.candidate_id = candidate_id

        # 检查报告记录代码、规格、测试集、验证器和环境版本；不一致则不能通过
        if not evidence.matches(candidate_id, spec):
            stop("NEEDS_HUMAN", "报告对应的代码或验收规格与本次任务不一致")
        if evidence.status == "UNKNOWN":
            stop("NEEDS_HUMAN", evidence.missing_requirements)

        # 只有全部必需检查通过，且代码未再次修改，才标记任务完成
        if evidence.status == "PASS" and evidence.all_required_executed:
            assert snapshot_hash(candidate) == candidate_id
            stop("ACCEPTED", "当前版本已通过约定范围内的全部检查")

        # ITERATE：按固定测试比较失败是否减少，不使用模型自评分
        improved = strict_progress(state.previous_evidence, evidence)
        state.stalled_rounds = 0 if improved else state.stalled_rounds + 1
        state.attempted.append(summary(plan, evidence))  # 避免重复无效尝试
        state.previous_evidence = evidence
        state.next_action = choose_next_from_failures(evidence)
        atomic_checkpoint(state)  # 每轮结束保存当前失败与下一步

        if state.stalled_rounds >= spec.max_stalled_rounds:
            stop("NO_PROGRESS", "相同验收标准下连续多轮失败用例没有减少")

    stop("LIMIT_REACHED", "已达到最大轮数")

except BudgetLimit as error:
    state.finish("LIMIT_REACHED", error.reason)  # 调用前拒绝超预算操作
except DeadlineExceeded as error:
    state.finish("LIMIT_REACHED", error.reason)  # 时限触发，工具已取消
except PlannedStop as result:
    state.finish(result.status, result.reason)  # 记录预定停止条件对应的状态和原因
except Exception as error:
    state.finish("NEEDS_HUMAN", safe_error(error))  # 无法处理的异常转交人工，不标记完成
finally:
    state.actual_usage = budget.current_ledger()  # 包含失败、取消与子代理消耗
    try:
        atomic_checkpoint(state)  # 所有退出均尝试保存，包含最终失败
    except SaveError:
        state.finish("NEEDS_HUMAN", "状态落盘失败；禁止后续变更")
        emit_report(state, persisted=False)  # 报告状态保存失败，不能承诺可恢复到当前进度
    else:
        emit_report(state, persisted=True)  # 输出检查报告、停止原因及恢复任务所需的信息

# 模型、工具和子代理均通过此函数调用，统一检查资源限制
def bounded_call(operation, payload, maximum_cost):
    check_total_deadline()  # 先检查整项任务的剩余运行时间
    ticket = budget.reserve(maximum_cost)  # 调用前保存本次额度预留；余额不足则不发起
    # reserve 将预留额完整写入账本；恢复后继续累计已用和未结算额度
    handle = None
    try:
        # 被调用程序必须能限制消耗；无法设置额度上限时不自动执行
        handle = operation.start(payload, hard_cap=ticket.limit)
        timeout = min(PER_CALL_TIMEOUT, remaining_total_time())
        return handle.wait(timeout=timeout)
    except Timeout:
        handle.cancel()  # 超时后发送取消请求，并检查后台操作是否停止
        if not handle.wait_until_stopped(CANCEL_GRACE):
            quarantine_workspace()  # 无法确认取消时隔离工作区，阻止后续写操作
            stop("NEEDS_HUMAN", "操作未确认停止，需要人工处理")
        raise DeadlineExceeded("单次调用超时，未采用该次输出")
    finally:
        # 成功、失败和取消均记录消耗；用量未知时不释放已预留额度
        budget.settle_or_keep_reserved(ticket, usage_if_known(handle))

def atomic_checkpoint(state):
    temporary = same_directory_temp(state.path)  # 在状态文件同一目录创建临时文件，以支持原子替换
    write_all(temporary, serialize(state))  # 先写完整的新状态文件，保留旧状态文件
    flush_and_fsync(temporary)  # 数据同步后再替换
    atomic_replace(temporary, state.path)  # 采用平台支持的原子替换操作
    sync_directory_if_supported(state.path)  # 按操作系统要求同步目录，保证文件替换记录写入存储

实际实现需要按操作系统验证取消操作、文件替换和断电后的恢复行为。工具超时后，运行环境必须确认后台操作已停止；只停止等待结果，后台操作仍可能继续。

  • 任务栈、水位、优先级与 FreeRTOS 调度影响。
  • 溢出、丢字节、长期吞吐与超时恢复。
  • 烧写、复位后的真实设备行为与逻辑分析仪测量。

上述硬件动作未执行，不能由宿主机单测代替并标为通过。

修改前确定测试用例和预期结果

用例组输入构造必须观察的结果
完整帧 / 分片完整帧；在帧内每个位置切成两段；逐字节输入。仅收齐并校验成功后输出一次；未收齐保留状态。
粘包 / 多帧两个或多个合法帧一次输入，末尾带半帧。完整帧顺序输出，尾部半帧留待下一次输入。
长度边界LEN = 0、64、65；不足以构成合法帧的数据。按规格接受边界值；越界长度拒绝，不越界读写。
校验错误 / 恢复修改 CRC 字节；错误帧之后追加合法帧。错误帧不输出；按重新同步策略找到后续合法帧。
噪声 / 假帧头随机前缀、重复 AA、载荷中出现 AA 55。长度与校验共同决定边界；每次处理有有限工作量。
属性 / 回归同一字节流采用不同切分；固定随机种子生成输入。不同切分产生相同合法帧序列；宿主机检测无非法访问。

第 0 轮 · 记录初始代码、测试和任务范围

把帧规格、CRC 约定、测试集和代码版本写入任务状态。先复现分片丢失，再将失败输入保存为最小样例。测试组数量不等于模拟台中的十个简化检查点。

第 1 轮 · 保留不完整帧

本轮修改：接收不足完整帧时返回“等待更多数据”，保留缓存。验证重点：分片成功，同时多帧解析和错误恢复没有回归。

第 2 轮 · 先验证长度，再计算访问范围

本轮修改：在访问载荷或 CRC 前检查 LEN 上限、累计长度与缓存剩余容量。验证重点：边界输入被正确处理，越界样例被拒绝。

第 3 轮 · 实现重新同步策略，运行完整回归

本轮修改：错误帧不会让解析器永久停在同一位置；新一轮必须消费字节、产生帧或等待新输入。全部必需宿主机检查通过后，保存被测代码和对应报告。

交付 · “宿主机验收通过，实板验证待执行”

报告修改范围、固定测试结果、尚未覆盖的条件和待执行的设备检查。若完成条件（Done）包含实板验收，则状态保持 NEEDS_HUMAN，等待人工处理，不能提前标记整项任务完成。

展开：解析器伪代码与中文注释
# 伪代码说明长度检查和字节处理过程；CRC 参数由事先确定的规格提供
def feed(bytes):
    append_with_capacity_policy(bytes)  # 满缓存如何丢弃/报错由规格定义
    while buffered_length() >= MIN_FRAME_LENGTH:
        if not starts_with_header(0xAA, 0x55):
            consume(1)  # 跳过一个噪声字节，再寻找帧头，避免重复检查同一位置
            continue
        length = peek_length()  # 当前已具备最短帧长度，读取 LEN 是安全的
        if length > MAX_PAYLOAD:
            consume(1)  # 长度超限时丢弃一个字节，按协议规定重新寻找帧头
            continue
        needed = HEADER_SIZE + LENGTH_SIZE + length + CRC_SIZE
        if buffered_length() < needed:
            return NEED_MORE  # 半帧保留，等待后续字节，不在原地忙循环
        if not crc_matches(peek(needed), LOCKED_CRC_SPEC):
            consume(1)  # CRC 错误不输出；此处采用教学上的逐字节重新同步
            continue
        emit(copy_payload(length))  # 复制载荷后再输出，避免调用方引用已移动的接收缓存
        consume(needed)  # 合法帧处理完毕，继续解析后面可能粘连的帧

若头部看似合法但长度对应的数据迟迟不到，何时丢弃待确认帧应由协议超时/恢复规格决定。不要让 AI 为了通过当前测试自行猜测协议语义。

成本计算与人工时间统计

提供给模型的信息、执行轮数、独立审查、测试资源和人工复核都会影响成本。若每轮附上全部历史记录，输入会持续增加。保存摘要、使用缓存和只读取修改部分，可以减少重复输入。

TOTAL COST

一次任务的成本构成

C = Σ(输入成本 + 输出成本)
　 + 工具 / 计算 / 设备成本
　 + 人工复核 / 返工成本
　 + 分摊的建设与维护成本

按实际模型、计费方式、缓存命中和重试统计。失败、取消和子代理工作也要计入。

ACCEPTED OUTCOME

需要同时记录的四项指标

  • 每个验收通过结果的成本：总成本 ÷ 通过数量。
  • 人工时间：复核、返工与故障接管所需时间。
  • 质量：验收后发现的缺陷、错误标记通过的次数及新增故障。
  • 交付时间：从启动任务到代码或文件通过验收的总耗时。

常见问题与处理方法

失败模式可观察信号工程处理
自我评分替代验收模型评分上升，但实际测试失败数量没有减少。必须通过事先确定的外部检查；模型自评只辅助定位。
执行过程修改原定验收标准删除或跳过失败用例、降低阈值后，检查才显示通过。保护验收配置；独立审查测试变化。
旧报告套用新代码代码变了，仍引用上轮通过结果。报告记录代码、规格、测试和环境版本；任一变化后重新检查。
反复修改但失败数量不变失败集合不变，反复提交同类补丁。记录已试方案；达到无进展上限后停止并报告。
环境故障被当产品缺陷设备不在线、工具链缺失，却不断改代码。区分 FAIL 与 UNKNOWN；环境故障只重试规定次数，仍失败则转交人工。
超时只是停止等待控制器退出，后台任务仍修改文件。取消并确认终止；无法确认则隔离工作区。
重启后重复执行写入操作重复发布、重复工单或同一设备被并发占用。幂等键、运行锁、持久状态与可恢复步骤。
上下文无限增长每轮输入增加、成本上升，关键日志和失败记录不易定位。保存摘要和日志路径，只读取相关内容，同时保留完整日志。
任务未完成时也需要输出报告。列出修改内容、检查结果、未完成项、停止原因和负责后续处理的人，使下一位工程师可以继续处理。

适用条件与实施步骤

先检查下面四项条件，再决定是否建设闭环。任务频率会影响建设成本能否被节省的人时抵消，不能统一规定为“每周至少一次”。

01 / REPEATABILITY

任务会重复出现吗？

同类任务可以重复使用已经配置的流程，减少每次人工操作。一次性任务也可以根据检查结果进行几轮修改，但未必需要长期自动运行。

02 / REJECTABILITY

系统能自动识别不合格结果吗？

需要能够执行的检查标准。若最终质量依赖审美或业务判断，可由系统生成初稿，再由人工验收。

03 / EXECUTABILITY

Agent 能执行任务需要的全部操作吗？

Agent 需要能访问代码、运行构建和测试，并已获得必要操作权限。硬件插拔或缺少访问凭据时，应明确交给人工处理。

04 / DEFINABLE DONE

“完成”是否能被客观判定？

写明需要提交的代码或文件、必需检查和检查范围。例如明确要求“宿主机协议测试全部通过”，避免只写“驱动足够稳定”。

STEP 1

先由人工完整执行

使用真实输入完成操作、检查和失败处理，记录正确步骤和人工耗时。

STEP 2

将步骤写入 Skill

保存可重复使用的步骤、限制条件和模板，删除只适用于一次任务的信息。

STEP 3

实现执行与检查循环

增加验收检查、状态保存、预算限制、停止和恢复逻辑，验证失败处理。

STEP 4

最后加入调度

设置触发规则，防止并发冲突和重复执行，记录运行状态及每个通过结果的成本。

首个试点可限定为：一个仓库、一个纯软件模块、一套固定测试和少量轮次，最终提交修改后的代码与检查报告。确认运行可靠后，再增加跨系统操作和设备验证。

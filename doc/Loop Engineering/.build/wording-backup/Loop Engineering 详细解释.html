01

先分清：你在设计哪一层？

一次请求产出一个候选结果；闭环负责判断结果是否达标，再决定推进、重试或停机。它是系统设计方法，不要求某个特定模型或工具。

层次主要设计对象UART 解析器示例
Prompt Engineering这一次，如何说明任务、约束和输出格式“补齐分片输入逻辑，并解释变更。”
Context Engineering本次推理能看到哪些正确、必要的信息注入帧规格、现有代码、失败样例与上一轮结论。
Harness Engineering围绕 agent 的运行设施与控制边界工作区、工具接口、测试执行、超时、权限与日志。
Loop Engineering如何用反馈持续推进，并可靠判断何时停止修复 → 跑固定测试 → 读取证据 → 再修复或退出。

02

五步一轮，让失败成为下一步的输入

点击阶段查看输入、动作和产物。DISCOVER 可以在首次全面执行，后续只更新变化与失败信息；五步是逻辑职责，不意味着每一步都要调用模型。

DISCOVER / 输入边界

先确认真正要解决的问题

收集规格、当前版本、失败证据与环境状态。区分产品缺陷、测试缺陷和工具故障；缺少关键协议约定时保留未知，不自行编造。

当前案例
输入：固定帧规格、解析器代码与跨两次接收的失败样例。
产物：一项可复现问题——第二次输入到来前，解析器错误丢弃了半帧。
交付给下一步：明确的缺陷与验收范围
VERIFY

把“好像完成”变成判定

由规格锁定的测试、静态检查和必要的外部测量给出结果。模型自评分可以辅助诊断。

STATE

让下一轮知道发生过什么

保存尝试、差异、失败证据和下一步。重启后可恢复，避免重复无效方案。

STOP

让失败也有明确的终点

成功之外，还要处理预算、超时、轮数、无进展、不可恢复故障和人工接管。

03

五个构件，各自承担一种职责

完整自动化经常用到下面的构件；最小闭环可以先从一个执行器、一个验证器和一个有状态的控制器开始。

01

触发 / 调度

手动、事件或定时启动任务；处理重复触发、互斥和运行窗口。

何时开始一轮任务
02

Skill

保存可复用步骤、输入约定、验收规则与不可修改范围。

如何稳定地做同一类事
03

执行 / 审查角色

执行者产出变更，审查者寻找遗漏。可由子代理分工，也可先用单代理。

分离职责，降低自我认可
04

工具 / 连接器

读写工作区、运行构建、查询工单与调用设备；限制范围并记录操作。

让计划进入真实环境
05

验证器

用独立验收规则拒绝坏输出，区分通过、失败与证据不可得。

决定候选是否可以被接受
定时任务 ≠ 反馈闭环。每小时重新执行一条提示，只解决“再次启动”；把验证结果和状态交给下一次决策，才解决“持续推进”。独立审查也不能替代外部测试。
04

验证强度，决定“完成”有多可信

验收条件必须在执行前确定，绑定本次候选版本。不同检查覆盖不同风险，需要组合；测试通过只支持它实际覆盖的范围。

证据层能证明什么不能单独证明什么
模型自检 / 评分候选是否明显偏离要求，是否存在可疑逻辑。运行正确性、安全性、时序行为；高分不是通行证。
独立审查另一个角色按检查表寻找遗漏、边界和不一致。两个模型意见一致仍可能共同出错。
机器可执行检查构建、静态规则、固定用例、属性测试在声明环境下的结果。未测输入、实板电气行为、长期稳定性。
外部系统 / 硬件证据指定固件、板卡和测量条件下，实际运行满足明确要求。不同硬件版本或未覆盖环境同样正确。
FREEZE THE GATE

让“修通过”不等于“改宽标准”

  • 锁定验收规格与关键测试版本。
  • 执行者不能自行删用例、跳过检查或降低阈值。
  • 发现规格或测试有误，单独提出修改并重新确认验收。
  • 保留隐藏/独立回归用例，降低只迎合已知测试的风险。
BIND THE EVIDENCE

证据必须属于这份产物

  • 候选代码哈希 / 提交标识。
  • 规格哈希、测试集哈希与验证器版本。
  • 构建环境、工具链和设备标识（如适用）。
  • 检查命令、退出码、日志或报告位置及时间。
PASS / FAIL / UNKNOWN 三态判定。检查未执行、工具超时、设备断开或证据与当前版本不一致，都应为 UNKNOWN。未看到失败，不等于已经通过。
05

保存进展，也保存停止的理由

持久状态让系统恢复任务，不代表模型在训练或参数发生改变。每轮只带入必要摘要，需要定位时再读取详细日志。

CHECKPOINT

一份够用的状态记录

STOP POLICY

让每个出口都可解释

状态触发条件
ACCEPTED当前版本的全部必需证据通过。
LIMIT_REACHED调用前预算不足，或达到总时限/轮数。
NO_PROGRESS连续规定轮数未产生有效进展。
NEEDS_HUMAN规格未知、设备不可用、风险越界或无法恢复。

“有效进展”预先定义：例如同一测试集下，失败集合严格减少且没有引入回归。模型更乐观、文本更长、重复同一补丁，都不算证据。

写状态时采用同目录临时文件 → 同步落盘 → 原子替换。每轮保存，所有退出路径再保存一次；恢复时核对工作区与证据版本，失配就重新验证。重要外部操作采用幂等键，避免重跑后重复提交。循环本身不保证收敛，因此无进展与资源触限都是必要出口。

把循环写成可审查的控制程序

下面是 Python 风格伪代码，用于说明控制边界；辅助函数是接口约定，并非可直接运行的 SDK。重点看调用前预算、三态验证、进度证据、原子保存和所有失败出口。

# 先冻结目标与验收；执行者不可自行修改规格、门禁和受保护测试
spec = load_locked_spec()
state = load_or_create_checkpoint(spec.task_id)

try:
    assert_resume_compatible(state, spec)  # 核对规格、工作区；失配转人工
    while state.round < spec.max_rounds:
        check_total_deadline()  # 使用持久化任务起始时间，恢复后不重置
        state.round += 1
        atomic_checkpoint(state)  # 调用前持久登记轮次，崩溃恢复不重复获得轮次

        # DISCOVER：只读取必要上下文；缺少关键协议约定时保留未知
        context = collect_context(spec, state, bounded_call)
        if context.has_blocking_unknown:
            stop("NEEDS_HUMAN", context.unknowns)

        # PLAN：结合失败证据与已试方案，选一个最小、可验证的下一步
        plan = bounded_call(planner, context, spec.plan_budget_cap)
        enforce_scope(plan, spec.allowed_paths, spec.allowed_actions)

        # EXECUTE：所有模型、工具和子代理调用统一经过预算与超时封装
        candidate = bounded_call(executor, plan, spec.execute_budget_cap)
        candidate_id = snapshot_hash(candidate)  # 验证期间锁住这份快照

        # VERIFY：在固定测试与环境中检查；超时/跳过/缺日志都不是通过
        evidence = bounded_call(verifier,
            (candidate_id, spec.locked_acceptance), spec.verify_budget_cap)
        state.evidence_ref = save_evidence(evidence)
        state.candidate_id = candidate_id

        # 证据绑定代码、规格、测试集、验证器和环境；失配则不可接受
        if not evidence.matches(candidate_id, spec):
            stop("NEEDS_HUMAN", "证据与当前候选或验收规格不一致")
        if evidence.status == "UNKNOWN":
            stop("NEEDS_HUMAN", evidence.missing_requirements)

        # 只有全部必需检查明确通过，且产物未再改变，才允许接受
        if evidence.status == "PASS" and evidence.all_required_executed:
            assert snapshot_hash(candidate) == candidate_id
            stop("ACCEPTED", "当前版本已通过约定范围内的全部检查")

        # ITERATE：进展来自固定标准下的新证据，不使用模型自评分
        improved = strict_progress(state.previous_evidence, evidence)
        state.stalled_rounds = 0 if improved else state.stalled_rounds + 1
        state.attempted.append(summary(plan, evidence))  # 避免重复无效尝试
        state.previous_evidence = evidence
        state.next_action = choose_next_from_failures(evidence)
        atomic_checkpoint(state)  # 每轮结束保存当前失败与下一步

        if state.stalled_rounds >= spec.max_stalled_rounds:
            stop("NO_PROGRESS", "固定验收下连续多轮没有有效进展")

    stop("LIMIT_REACHED", "已达到最大轮数")

except BudgetLimit as error:
    state.finish("LIMIT_REACHED", error.reason)  # 调用前拒绝超预算操作
except DeadlineExceeded as error:
    state.finish("LIMIT_REACHED", error.reason)  # 时限触发，工具已取消
except PlannedStop as result:
    state.finish(result.status, result.reason)  # 统一记录成功或受控退出
except Exception as error:
    state.finish("NEEDS_HUMAN", safe_error(error))  # 未知异常不伪装成功
finally:
    state.actual_usage = budget.current_ledger()  # 包含失败、取消与子代理消耗
    try:
        atomic_checkpoint(state)  # 所有退出均尝试保存，包含最终失败
    except SaveError:
        state.finish("NEEDS_HUMAN", "状态落盘失败；禁止后续变更")
        emit_report(state, persisted=False)  # 明确报告未保存，不伪称可恢复
    else:
        emit_report(state, persisted=True)  # 输出证据、停止原因与恢复入口

# 所有会消耗资源的调用共用这一封装，包含模型、工具与子代理
def bounded_call(operation, payload, maximum_cost):
    check_total_deadline()  # 先检查整项任务的剩余运行时间
    ticket = budget.reserve(maximum_cost)  # 调用前持久预留硬上限；不足则不发起
    # reserve 原子写入持久账本，恢复时沿用已用与未结算预留额，不重新发放
    handle = None
    try:
        # 下游必须能执行额度上限；不能限制消耗的操作不纳入无人值守
        handle = operation.start(payload, hard_cap=ticket.limit)
        timeout = min(PER_CALL_TIMEOUT, remaining_total_time())
        return handle.wait(timeout=timeout)
    except Timeout:
        handle.cancel()  # 超时后主动取消，不允许后台继续修改或计费
        if not handle.wait_until_stopped(CANCEL_GRACE):
            quarantine_workspace()  # 取消未确认时隔离产物，阻止后续写操作
            stop("NEEDS_HUMAN", "操作未确认停止，需要人工处理")
        raise DeadlineExceeded("单次调用超时，未采用该次输出")
    finally:
        # 成功、失败和取消均结算；用量未知时保留预留额，禁止虚假退款
        budget.settle_or_keep_reserved(ticket, usage_if_known(handle))

    write_all(temporary, serialize(state))  # 先完整写出，不覆盖旧检查点
    flush_and_fsync(temporary)  # 数据同步后再替换
    atomic_replace(temporary, state.path)  # 采用平台支持的原子替换操作
    sync_directory_if_supported(state.path)  # 按操作系统补足持久化语义
    # 保存失败时立即报告并停止继续变更；不得把检查点失败当作成功

真实实现还需要按平台验证取消、原子替换和断电恢复语义。工具超时后是否真正停止，必须由运行设施确认；光停止等待并不能停止后台操作。

工程案例：UART 流式协议解析器

以下是原创教学案例，所有问题、轮次与结果均为假设，不是实测记录。任务范围先限定为宿主机上的纯解析逻辑，目标是正确处理任意分片输入。

AA 552 字节固定帧头
LEN1 字节 · 载荷长度
PAYLOAD0…64 字节 · 教学上限
CRC162 字节

教学约定：LEN 只计载荷；接收缓存容量受控。CRC 多项式、初值、输入/输出反射、最终异或、覆盖字节与字节序必须由协议规格锁定，此处不臆造。采集层只提供字节流，不保证一次接收就是一帧。

GOAL & SCOPE

把目标收缩到可以证明的范围

  • 任意分片和连续多帧输入都能恢复完整合法帧。
  • 长度越界、CRC 错误、噪声与不完整输入不会越界访问。
  • 错误后按固定重新同步策略恢复，避免无限扫描。
  • 接口与正确行为保持不变；宿主机检查全部通过。
NOT YET VERIFIED

另建实板验收清单

  • UART 中断 / DMA 缓冲交接和并发一致性。
  • 任务栈、水位、优先级与 FreeRTOS 调度影响。
  • 溢出、丢字节、长期吞吐与超时恢复。
  • 烧写、复位后的真实设备行为与逻辑分析仪测量。

上述硬件动作未执行，不能由宿主机单测代替并标为通过。

先固定测试矩阵，再允许修复

用例组输入构造必须观察的结果
完整帧 / 分片完整帧；在帧内每个位置切成两段；逐字节输入。仅收齐并校验成功后输出一次；未收齐保留状态。
粘包 / 多帧两个或多个合法帧一次输入，末尾带半帧。完整帧顺序输出，尾部半帧留待下一次输入。
长度边界LEN = 0、64、65；不足以构成合法帧的数据。按规格接受边界值；越界长度拒绝，不越界读写。
校验错误 / 恢复修改 CRC 字节；错误帧之后追加合法帧。错误帧不输出；按重新同步策略找到后续合法帧。
噪声 / 假帧头随机前缀、重复 AA、载荷中出现 AA 55。长度与校验共同决定边界；每次处理有有限工作量。
属性 / 回归同一字节流采用不同切分；固定随机种子生成输入。不同切分产生相同合法帧序列；宿主机检测无非法访问。

第 0 轮 · 冻结基线与范围

把帧规格、CRC 约定、测试集和代码版本写入任务状态。先复现分片丢失，再将失败输入保存为最小样例。测试组数量不等于模拟台中的十个简化检查点。

第 1 轮 · 保留不完整帧

候选修复：接收不足完整帧时返回“等待更多数据”，保留缓存。验证重点：分片成功，同时多帧解析和错误恢复没有回归。

第 2 轮 · 先验证长度，再计算访问范围

候选修复：在访问载荷或 CRC 前检查 LEN 上限、累计长度与缓存剩余容量。验证重点：边界输入被正确处理，越界样例被拒绝。

第 3 轮 · 锁定重新同步策略，跑完整回归

候选修复：错误帧不会让解析器永久停在同一位置；新一轮必须消费字节、产生帧或等待新输入。全部必需宿主机检查通过后，保存对应代码与报告。

交付 · “宿主机验收通过，实板验证待执行”

报告变更范围、固定测试结果、残留限制和待执行的设备检查。若任务的 Done 本就包含实板验收，则状态保持 NEEDS_HUMAN，不能提前标记整项任务完成。

展开：有中文注释的解析器形态示意
# 伪代码只表达边界与进展约束；CRC 具体参数来自已锁定规格
def feed(bytes):
    append_with_capacity_policy(bytes)  # 满缓存如何丢弃/报错由规格定义
    while buffered_length() >= MIN_FRAME_LENGTH:
        if not starts_with_header(0xAA, 0x55):
            consume(1)  # 有限推进：跳过一个噪声字节后重新寻找帧头
            continue
        length = peek_length()  # 当前已具备最短帧长度，读取 LEN 是安全的
        if length > MAX_PAYLOAD:
            consume(1)  # 拒绝超长声明，按规格重新同步，不信任远端长度
            continue
        needed = HEADER_SIZE + LENGTH_SIZE + length + CRC_SIZE
        if buffered_length() < needed:
            return NEED_MORE  # 半帧保留，等待后续字节，不在原地忙循环
        if not crc_matches(peek(needed), LOCKED_CRC_SPEC):
            consume(1)  # CRC 错误不输出；此处采用教学上的逐字节重新同步
            continue
        emit(copy_payload(length))  # 明确复制/所有权，避免缓存移动后悬空引用
        consume(needed)  # 合法帧处理完毕，继续解析后面可能粘连的帧

若头部看似合法但长度对应的数据迟迟不到，何时丢弃候选帧应由协议超时/恢复规格决定。不要让 AI 为了通过当前测试自行猜测协议语义。

09

成本看“被接受的结果”，也看节省的人时

长上下文、多轮反馈、独立审查、测试机器与人工复核都会产生成本。上下文若不断累积，每轮输入会变大；摘要、缓存与增量读取可改变增长曲线。

TOTAL COST

一次任务的成本构成

C = Σ(输入成本 + 输出成本)
　 + 工具 / 计算 / 设备成本
　 + 人工复核 / 返工成本
　 + 分摊的建设与维护成本

按实际模型、计费方式、缓存命中和重试统计。失败、取消和子代理工作也要计入。

ACCEPTED OUTCOME

至少同时跟踪四项

  • 单位被接受结果成本：总成本 ÷ 接受数。
  • 人工时间：复核、返工与故障接管所需时间。
  • 质量：逃逸缺陷、误接受和回归情况。
  • 交付时间：从触发到可接受产物的总耗时。

最危险的失败，是没有证据却宣布成功

失败模式可观察信号工程处理
自我评分替代验收答案越来越自信，外部失败没有减少。以固定外部检查为门禁；自评只帮助定位。
验收标准随修复漂移删用例、加跳过、改阈值后变绿。保护验收配置；独立审查测试变化。
旧报告套用新代码代码变了，仍引用上轮通过结果。代码、规格、测试与环境哈希绑定；变更即失效。
重复绕圈 / 无进展失败集合不变，反复提交同类补丁。记录已试方案；达到无进展上限后停止并报告。
环境故障被当产品缺陷设备不在线、工具链缺失，却不断改代码。区分 FAIL 与 UNKNOWN；有限基础设施重试后交人工。
超时只是停止等待控制器退出，后台任务仍修改文件。取消并确认终止；无法确认则隔离工作区。
重启导致重复副作用重复发布、重复工单或同一设备被并发占用。幂等键、运行锁、持久状态与可恢复步骤。
上下文无限增长每轮输入增加，成本上升且重要证据被淹没。摘要 + 证据索引；只重读相关片段，保留完整日志。
失败报告也是有效产物。它应说明已修改什么、验证了什么、缺少什么、为什么停止、下一步由谁做；只输出“未能完成”不足以接续工程工作。
11

先可靠，再复用；先闭环，再调度

先回答四个问题，再决定是否值得投入闭环。频率只影响回报周期，不存在适用于所有团队的固定“每周一次”门槛。

01 / REPEATABILITY

任务会重复出现吗？

同类缺陷修复、固定规则的检查与批量迁移可摊薄建设成本。一次性任务也能使用轻量反馈，但未必需要长期自动化。

02 / REJECTABILITY

系统能自动拒绝坏输出吗？

必须有可执行标准；若只能靠审美或业务判断，就让系统生成候选，保留人工验收。

03 / EXECUTABILITY

agent 能端到端完成所需动作吗？

代码、构建、测试与必要工具都在可访问且已授权的范围内。硬件插拔或缺失凭据应成为明确的人工节点。

04 / DEFINABLE DONE

“完成”是否能被客观判定？

写出具体产物、验收证据与覆盖边界。例如“宿主机协议测试通过”，比“驱动足够稳定”更可执行。

STEP 1

人工可靠跑通

从真实输入走完执行、检查、失败处理和交付，记录基线。

STEP 2

固化为 Skill

提炼步骤、边界与模板，剔除只对一次任务有效的细节。

STEP 3

包成可控闭环

接入门禁、状态、预算、停机与恢复，覆盖失败路径。

STEP 4

最后加入调度

设置触发、互斥、去重、监控与通知，观察实际接受成本。

首个试点可以限定为：一个仓库、一个纯软件模块、一套固定测试、少量轮次、产出候选变更。稳定后再扩展到跨系统操作与设备验证。

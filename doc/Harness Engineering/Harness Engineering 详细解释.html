01

定义与边界

Harness Engineering 是围绕模型设计运行环境、执行约束、反馈和状态管理的工程实践。它改善的是整个系统的工作方式。

CONTEXT

让模型看见正确的现场

工作目录、代码版本、模块契约、可用工具、尚未完成的任务和最新验证结果。上下文要按需加载，并保留来源位置与时效。

CONTROL

把动作放进明确边界

允许访问的路径、命令、网络、设备与时间预算由程序约束。模型可以提议动作，执行权限由宿主环境决定。

EVIDENCE

用可复核证据决定进度

保存命令、退出码、测试结果、环境与代码版本。结果不满足契约时，修正、升级处理或停止；不能仅凭模型自述标记完成。

用操作系统类比理解职责

类比对象帮助理解的职责类比到这里就该停下
模型 ≈ CPU承担理解、规划和生成的核心计算。模型是概率性推理系统；并不具备 CPU 指令级确定性，也不是执行命令的主体。
上下文窗口 ≈ RAM提供当前工作集，容量有限，需要取舍和更新。上下文不是可随机寻址的可靠存储；“在窗口里”不等于“被正确使用”。
Harness ≈ OS管理工具、调度、状态、资源预算与边界。提示词无法提供内核级隔离；实际安全边界来自沙箱、操作系统权限及服务端鉴权。
成功条件：面对相同任务，整个系统能更稳定地产生满足验收的变更，并能解释每次失败、续接工作和控制成本。它不能保证模型永不出错。

03

Prompt、Context、Loop 与 Harness

四个视角可以重叠；它们描述的是不同层次的问题，术语边界也并非统一标准。

视角核心问题典型设计只做这一层的缺口
Prompt Engineering这一轮如何表达任务？目标、约束、输出格式、必要示例。无法单独解决状态、权限和真实验证。
Context Engineering这一刻应该提供哪些信息？检索代码、裁剪日志、模块索引、记忆恢复。信息正确，也仍可能执行错误或跳过验收。
Loop Engineering怎样持续推进、纠错和停止？观察 → 规划 → 行动 → 评价 → 选择下一步。循环本身不会自动提供可信工具与执行边界。
Harness Engineering怎样让完整系统稳定交付？统筹上下文、工具、循环、恢复、证据和预算。仍需要清晰需求、可靠环境和工程判断。

五项落地工件

先把工程事实写成可维护的工件，再让运行循环消费它们。文件名是示例，结构与责任才是重点。

01

AGENTS.md：项目入口与约束索引

说明目录职责、构建入口、验证方法、架构边界和禁改范围；链接仓库内部的设计文档。保持短而可导航，具体规则可下沉至模块。

维护要求：模块迁移、构建方式或架构约束改变时同步更新；路径和命令应能核验。

02

feature_list.json：任务状态与验收记录

每项包含稳定 ID、优先级、验收条目、状态和证据引用。它是进度账本；真正的测试脚本、环境和报告需要独立存在。

维护要求：完成标记必须由验收证据支撑；不能为了通过而删改验收条目。JSON 不支持注释，解释请放旁注或改用明确标注的 JSONC。

03

初始化例程：每个会话的已知起点

确认工作目录、分支和未提交变更；读取任务状态与近期提交；检查工具链和设备；运行适当的基线验证，再开始一个有边界的任务。

维护要求：可重复执行；不能清理掉别人的未提交修改。缺失依赖应显式报告。

04

任务契约：实施前固定验收口径

把目标、范围、非目标、风险、允许动作、验收方法及退出条件写清楚。规划、执行、评价可以分阶段完成，也可以由不同角色承担。

维护要求：只有在需求变化被确认后才更新验收；计划和评价的逻辑分离不意味着必须运行三个模型。

05

真实影响图：把任务绑定到仓库现场

列出已确认存在的文件、符号、调用链、既有模式及对应验证；同时标记尚待验证的推断。让后续补丁沿真实代码结构展开。

维护要求：每项包含定位依据；仓库重构后重新计算。示意路径不能直接当作当前项目事实。

05

任务契约与真实影响图

把“修一下串口丢包”转成可执行任务：先定义什么叫修好，再决定改动哪段代码。

TASK CONTRACT

实施前必须清楚的内容

目标：在约定输入速率、调度负载和接收容量下，满足数据完整性要求。

范围：接收数据路径、必要的统计和测试；接口兼容要求明确。

非目标：不顺带重构协议栈，不改变发送路径。

验收：边界条件测试、目标构建、硬件测试条件和报告字段预先定义。

退出：缺少板卡为 blocked；预算或重试耗尽为 failed；全部要求通过才为 completed。

GROUNDED IMPACT MAP

用代码检索验证每个候选点

入口：确认真实中断、DMA 回调及注册位置。

数据流：追踪“DMA 写入 → 生产者索引 → 任务消费 → 协议处理”。

同步：检查索引的读写上下文、可见性和互斥约定。

既有模式：查找相邻驱动如何处理通知、缓冲区与溢出。

变更边界：逐项标出文件、符号、影响的调用方及验证入口。

把未知保留为未知：“怀疑环回边界重复消费”属于待验证假设；“某符号负责消费索引推进”只有在实际代码定位后才能写成事实。

读取现场与当前验收契约

running

检查代码版本、未提交变更、任务状态与验证基线。准备处理一个有边界的任务。

步骤 1 / 6修正重试 0 / 2证据：已读取基线

completed：约定验收全部满足　｜　blocked：存在外部前提缺口　｜　failed：当前尝试在规则或预算内无法完成。

规划、执行和评价如何分开

PLAN

产物是任务契约

定义最小变更、约束、验收与影响范围。它必须足够明确，执行者才能知道哪一步算越界。

EXECUTE

产物是受控变更

读取真实文件后实施小步改动。把执行结果、错误与环境状态原样交还控制层。

EVALUATE

产物是验收判断

运行独立的测试和门禁，必要时补充语义审查。评价者的语言判断不能覆盖失败的硬性验收。

可以在单一进程中分阶段，也可以按风险引入人工或不同代理。独立模型仍可能存在相关性错误，验收应尽量落在可执行的检查和真实环境上。

07

前馈 / 反馈 × 确定性 / 推理

从“何时使用”和“如何判断”两个维度分配控制。点击象限，查看嵌入式工作流中的使用方式与局限。

上：确定性检查　／　下：推理判断
前馈 · 约束下一次动作
反馈 · 评价已经产生的结果

确定性前馈 · 工具门禁

例：执行前解析补丁涉及的真实路径，拒绝越过允许模块的写入；烧录前校验目标设备身份与授权。

适合强制执行明确规则。规则过宽会漏掉风险，规则过窄会阻碍正常工作。
同一工具可以落在不同位置：把 linter 规则提供给实现阶段，是对下一步的前馈；对已生成的补丁运行 linter，是反馈。测试失败日志既是本轮结果的反馈，也成为下一轮修正的前馈。分类取决于它相对哪次动作发挥作用。

“确定性”描述按固定规则检查，不保证运行一定快速或可复现；硬件测试可能有时序噪声，LLM 推理也可能仅用于提出建议。两类控制需要组合使用。

把控制写进代码

下面是带中文注释的 Python 风格伪代码，用来解释控制顺序；函数与数据结构均为示意，不能直接运行。

run_task.pseudo · 主循环
# 初始化、模型、执行和验证共享总预算；数值仅为演示。
budget = create_budget(task.resource_limits, max_retries=2, max_stagnation=2)
resources = create_resource_scope()
state = initial_state(task)

try:
    # 恢复时重新核对基线；包装器实际执行超时与资源限制。
    state = run_bounded(restore_and_validate, task, repository,
                        budget=budget, resources=resources)

    while True:
        # 先检查运行边界和外部前提，准备本轮下一状态。
        # 恢复阶段已经识别的冲突或阻塞，直接保存并退出。
        if state.is_terminal:
            next_state = state
        elif budget.exhausted() or state.stagnation_limit_reached():
            next_state = state.stop("failed", "达到运行边界")
        elif state.required_external_dependency_missing():
            next_state = state.stop("blocked", state.missing_dependency)
        else:
            # 每轮都计数；模型规划也占用总时间与费用预算。
            budget.consume_iteration()
            context = build_context(task.contract, state, repository)
            proposal = run_bounded(model.propose_one_step, context,
                                   budget=budget, resources=resources)
            decision = guard(proposal, task.permissions, budget)

            # 拒绝也写入状态；重复越界会触发次数或停滞上限。
            if not decision.allowed:
                next_state = state.with_rejection(decision.reason)
            else:
                # 只执行获准动作，保留真实退出码与产物。
                result = run_bounded(execute, proposal, decision,
                                     budget=budget, resources=resources)

                # 固定受测代码和工具链；设备配置受控并持有租约。
                with frozen_validation_scope(repository, resources) as env:
                    evidence = run_bounded(verify_required_checks,
                        task.contract, env, budget=budget, resources=resources)
                    evidence.invalidate_if_environment_changed(env)

                # 先合并证据、分类失败，再推导下一状态与重试学习。
                next_state = derive_next_state(state, result, evidence,
                    contract=task.contract, budget=budget)
                # 该函数只按全任务必需验收判 completed，不按当前小步。
                # 缺外部条件为 blocked；不可重试或预算耗尽为 failed。

        # 下一状态含证据、预算、失败学习和终止原因，原子保存。
        checkpoint_atomically(next_state, budget)
        state = next_state

        # 保存成功后才对外返回；运行中状态继续下一轮。
        if state.is_terminal:
            return state.summary()

except RuntimeBudgetExceeded as error:
    # 包装器中断超时或超额操作，保留失败现场后结束。
    state = state.stop("failed", error.reason)
    checkpoint_atomically(state, budget)
    return state.summary()
finally:
    # 无论成功、失败或异常，都清理进程、快照和设备租约。
    resources.cleanup()
guard.pseudo · 动作门禁
# 所有工具调用通过统一入口，禁止绕过宿主权限策略。
def guard(action, permissions, budget):
    # 校验工具名、结构化参数和调用资源预算。
    if not schema_valid(action) or not budget.can_start(action):
        return deny("参数无效或预算不足")
    if action.tool not in permissions.allowed_tools:
        return deny("工具不在允许集合中")

    # 解析真实路径并处理链接；不能仅做字符串前缀匹配。
    for path in resolve_real_targets(action):
        if not permitted_path(path, action.operation, permissions):
            return deny("目标路径超出任务授权范围")

    # 网络、密钥和外部写入分别校验，防止工具扩大权限。
    if not external_access_allowed(action, permissions):
        return deny("外部访问未获任务授权")

    # 烧录、擦除等动作绑定具体设备，按既定授权流程执行。
    if action.affects_hardware:
        if not match_device_identity(action, permissions.device):
            return deny("设备身份不匹配")
        if not hardware_operation_authorized(action, permissions):
            return deny("该设备操作不在授权范围")

    # 返回允许只意味着可执行；执行后仍要验证结果。
    return allow(timeout=permissions.tool_timeout,
                 sandbox=permissions.execution_sandbox)
restore.pseudo · 恢复与验收
# 检查点提供线索，真实仓库、产物和环境提供当前事实。
def restore_and_validate(task, repository):
    saved = load_checkpoint(task.id)
    current = inspect_workspace_without_discarding_changes(repository)

    # 保留他人的未提交修改；有冲突时显式标记并停止相关动作。
    if conflicting_changes(saved, current):
        return blocked_state("工作区存在需要协调的变更")

    # 提交、补丁、工具链、配置或输入变化时，失效相关证据。
    state = reconcile(saved, current)
    state.invalidate_mismatched_evidence()

    # 对受影响范围重跑必要基线；不要默认沿用旧的通过状态。
    state.attach(run_required_baseline(task, current))
    return state

# 验收是逐项、逐版本的判断；没有报告的检查属于未验证。
def acceptance_passes(contract, evidence):
    # 空验收清单是无效契约，不能因为循环为空而通过。
    if not contract.required_criteria:
        return False
    for criterion in contract.required_criteria:
        report = evidence.find_current(criterion.id)
        if report is None or report.status != "passed":
            return False
        if not report.matches_tested_code_and_environment():
            return False

    # 硬件验收如被契约要求，主机模拟报告不能替代。
    if contract.requires_hil and not evidence.has_valid_hil_report():
        return False
    return True
落地时还要实现：预算预留与结算、状态转移校验、不可变快照、幂等恢复、工具与存储异常处理、日志脱敏及授权记录。持久化失败时不能宣告完成；须保留错误并走恢复流程。上面的封装函数展示责任边界，不是完整运行时实现。

跨会话：保存证据链，而非只存聊天

会话结束后，下一次运行应能回答：当前代码是什么、什么已经验证、哪些结论已经过期、下一步从哪里开始。

01 / TASK
任务与验收版本

任务 ID、契约版本、必需检查项与当前阻塞。

02 / CODE
受测代码指纹

提交 SHA；有未提交修改时补充补丁或工作树指纹。

03 / ENV
环境与输入

工具链、构建选项、测试数据、设备和固件身份。

04 / RESULT
可复核验证产物

命令、退出码、时间、完整报告、原始日志及哈希。

持久化内容下一会话如何使用需要防止的错误
进度摘要快速恢复目标、当前假设与下一步。摘要写“测试通过”，但找不到对应报告。
提交与补丁确认变更边界和受测版本，识别并行修改。测试后又修改了代码，却沿用旧通过结论。
证据清单按验收条目查找最新有效报告。把其他板卡、配置或固件的测试结果混用。
检查点从确定的阶段续接，避免重复高代价动作。崩溃后重复烧录、上传或其他非幂等动作。
“提交了”与“验证了”是两个状态。代码提交后若没有改动，之前对相同内容的证据可以在核对后关联到该提交；若内容、配置或环境发生变化，需要按影响范围重新验证。是否提交仍遵循项目工作流。

嵌入式案例：UART DMA 接收丢包

把 Harness 的每项职责映射到熟悉的工程工作。以下是虚构教学场景，没有关联真实板卡、日志或测试结果。

假设场景 · 用于方法推演 · 未经实测
FREERTOS × UART DMA × RING BUFFER

高负载时，接收数据偶发不完整

假设项目使用 DMA 接收，ISR 发布可用数据，FreeRTOS 任务从环形缓冲区消费。先补齐复现输入、运行负载、缓冲区容量与丢包判据，再做定位。

第一步：形成可复现的边界

明确 MCU 与缓存能力、DMA 工作模式、中断优先级、任务优先级、吞吐与突发长度、协议帧结构、预期容量和可接受溢出行为。

采集发送序号、接收序号、错误计数和缓冲区水位。区分线路错误、驱动丢失、队列溢出与上层处理积压。

第二步：明确完成需要哪些证据

算法边界测试验证索引计算；目标构建检查平台适配；硬件测试检验真实 DMA、ISR、调度和持续接收行为。

测试时长、输入负载、目标设备、观察指标和通过阈值由任务契约确定。本手册不提供虚构实测参数。

第三步：把怀疑点变成可证伪的假设

  • 环回边界处理：构造 DMA 写入位置跨尾部、空缓冲、满缓冲及重复事件，检查字节是否遗漏或重复消费。
  • 生产者 / 消费者并发：核对 ISR 和任务对索引的写入所有权及同步方式，用可控调度和真实压力运行验证。
  • 消费者处理不足：观测缓冲区水位、积压时长和溢出计数，区分吞吐不足与算法错误；不能仅凭“增大缓冲区后改善”就认定根因。
  • 条件相关的平台问题：只有目标架构和配置确实涉及缓存一致性、特定 DMA 约束时才展开检查，不假定所有 MCU 都有相同问题。

Harness 如何组织这次任务

系统职责具体安排产出
上下文检索实际驱动、ISR、消费任务和同步原语；读板级设计约束。经过代码定位的影响图；未验证假设单独标记。
工具与权限限定修改目录；编译器和主机测试可运行；设备操作绑定实际授权。可执行动作集合与设备身份检查。
执行循环选择一个假设 → 构造最小验证 → 检查证据 → 再决定是否修改。小步补丁、假设排除记录及关联测试。
状态与证据保存受测代码、工具链、固件指纹与原始输出。能被下一会话复核的验证清单。
完成门禁逐项检查必需验收；没有板卡时停止硬件验收。主机通过但硬件未验证 → blocked，而非 completed。
本案例的正确结论是方法，不是根因：尚未获得真实代码与测量数据，不能宣称丢包由某寄存器、缓存或环回算法造成，也不能宣称某补丁已经修复。
11

验证分层，失败分类

验证层次回答“能证明什么”；失败分类回答“下一步应该由谁解决”。两者共同决定是否继续运行。

L0

静态约束与改动检查

确认范围、接口、依赖、格式和显性缺陷。无法证明运行行为正确。

L1

主机单元与属性测试

覆盖算法、边界、数据不变量和错误路径。调度、硬件事件与内存模型可能被简化。

L2

目标构建与集成检查

检查目标工具链、配置、链接和模块集成。编译通过不代表运行时正确。

L3

HIL / 板级验证

检查真实 DMA、ISR、调度、外设与时序行为。必须记录设备、固件、输入和运行条件。

L4

系统回归与持续观测

检查持续负载、相邻功能、资源占用及运行稳定性。验收范围由项目风险决定。

主机测试不能替代 HIL。当硬件验收属于必需条目时，缺设备或访问权限就应保留已完成证据并标为 blocked。只完成算法级验证，必须把结论限制在算法层。

失败分类与处理策略

类别识别线索下一步
需求或验收歧义目标互相冲突，缺少通过标准。提炼最小待确认问题；依赖该信息的工作标 blocked。
实现缺陷可复现失败与补丁、输入存在对应关系。围绕一个假设做有限修正，用同一验收重新验证。
环境或依赖缺失工具链、服务、设备或权限不可用。在授权范围内修复环境；需要外部条件时 blocked。
证据失效代码、配置、输入或设备已变更。失效相关通过状态，重新运行受影响的检查。
偶发 / 不稳定测试同条件结果波动，缺少稳定复现。记录波动并调查；一次重跑通过不能抹去未解释的失败。
执行资源耗尽重试、费用、时间或停滞达到上限。保存现场并以 failed 结束当前尝试，给出后续建议。
12

预算、退出与真实成本

“自动运行”需要明确边界。持续调用模型不等于持续取得进展；便宜的一次调用也不等于便宜的一次交付。

RETRY

重试上限

针对同一失败限制修正次数；每次必须带着新假设或证据。

TIME

执行超时

工具超时和任务总超时分开控制，清理残留进程并保存现场。

COST

费用预算

统计模型调用、工具与执行资源，启动高代价动作前检查余量。

PROGRESS

停滞判断

同一错误、重复动作、无新证据持续出现时，结束无效循环。

用“每个验收通过的变更”计算成本

统计窗口内的总成本应包含失败尝试。分母采用通过约定验收的变更数，并同时观察耗时、成功率与回归情况。

INTERACTIVE CALCULATOR · 全部输入为教学示例，单位：元
¥100.00 / 变更(120 + 40 + 240) ÷ 4 = 100.00
公平比较需要相同口径：固定任务集合、验收强度、运行预算和环境；区分任务类型与风险等级。不能拿“只生成演示页面”的成本与“通过功能和硬件验收”的成本直接比较。

若验收通过数为 0，单位交付成本不可计算；此时报告总投入和失败原因。实际评估还应记录首次通过率、人工介入量、端到端耗时、回归逃逸和失败类别。

13

Harness 会衰减，组件要能被移除

模型、代码库和工具改变后，旧的补偿步骤可能不再划算；重复提示、冗余工具和多重评价会继续消耗时间与上下文。

WHAT TO WATCH

观察哪些组件可能已经失效

组件增加了调用，却很少改变决策；规则与仓库实际状态不一致；多个步骤重复加载同样的信息；工具重叠导致选择成本上升。

先核对使用数据，再判断它是否值得保留。模型升级只是重新评估的触发条件，不是删除验证的充分理由。

ABLATION

一次关闭一个组件做对照

选择代表性任务，固定验收与预算；比较启用和关闭该组件的效果。按任务风险和失败类别看差异，避免只比较平均成本。

证据不足时维持现状；回归时恢复配置。每个组件应能独立开关、观测并回退。

BASELINE建立任务基线
→

→

先区分两类约束：为补偿模型能力而增加的步骤，可以通过消融评估；权限隔离、设备授权、敏感信息保护、审计和必要验收属于工程边界，不能因模型“更聪明”就取消。调整边界需要独立的风险与授权判断。

常见误解

AGENTS.md 写得足够详细，Agent 就可靠了吗？

它只是信息与约定的入口。可靠性还需要真实上下文、受控工具、可执行验收、证据绑定和退出控制；长文档也会过期，并占用工作上下文。

评价者必须是另一个模型吗？

不必。编译器、测试程序、规则引擎、独立审查和人工评价可以按风险组合。逻辑上独立的验收标准更关键；另一个模型也无法代替真实硬件与客观测试。

feature_list.json 标记通过，就等于测试通过吗？

不等于。任务账本只记录状态。通过结论需要对应验收项的有效报告，并核对受测代码和环境；未运行、报告过期或硬件缺失都不能标为完成。

多加工具、规则和重试一定更好吗？

不一定。它们可能增加选择负担、误判和执行成本。先解决实际失效模式，再通过代表性任务评估收益；每次重试都应带来新信息。

模型升级后，可以直接删掉验证层吗？

不能仅据此决定。对能力补偿步骤做受控消融，同时保留与项目风险对应的验收、授权和审计边界；模型能力提升并不消除环境故障与集成风险。

没有设备时，交付什么才算诚实且有用？

交付已完成的代码分析、受控补丁、主机与构建验证报告、明确的硬件验收方案，并列出设备或权限缺口。若 HIL 属于必需验收，整体任务应标 blocked。

可执行的下一步：选一个边界明确的驱动问题，建立任务契约和证据目录；让模型提出一步、宿主检查一步、工具验证一步。先证明这个闭环能正确完成或正确停止，再扩大范围。

### 3.3 沿用 v1 的重要规则及验证适配

- 简单任务不强制多代理。需要拆分时先稳定公共契约，再并行处理真正独立的部分。
- 文件名不同不代表独立。头文件、ABI、线协议、构建配置、生成代码和测试夹具都可能带来隐含依赖。
- 同一公共文件有唯一写入者；worktree 隔离不能消除语义冲突。汇合后重验集成结果。
- 编码者自己自测，不必须另开“自测 Agent”；Reviewer 独立只读检查，不暗中改代码。
- 每个事先约定的验收切片，初始实现和初测之后，最多进行 3 轮修复。自测、Review、板端或模拟板端验证引发的修复共享该预算，不能改名、拆片或换阶段清零。这是当前模板约定，不是全项目永远只能修 3 次。
- 项目总预算没有给定时留空；扩大预算或改变验收需要用户决定。
- 证据绑定准确源码快照。仅有 HEAD 不足以代表带未提交修改的源码；文档证据也要绑定版本。
- host 单测、mock、交叉构建、板端验证和模拟板端验证的证据分别记录；不能把主机或模拟环境通过写成真实板端通过。
- 技术 PASS 不代替人工验收、合并、发布或部署批准。
- 状态区分 PASS、FAIL、BLOCKED、NEEDS_DECISION；缺环境不能抹去已知失败，模型信心不能补齐证据。
- 板卡互斥必须真实有效，文档写“加锁”不会生成锁；不能未经授权安装、提交、刷写或操作生产系统与实车执行器。

### 3.4 已澄清的 CLI 与 Skill 关系

此前 CLI 讨论指的是可供 Agent 调用的项目命令行工具，不仅是 Codex、Claude 或 Pi 本身。Skill 提供操作指导，真正的脚本或工具负责执行和产生证据。

`build.sh`、CTest、Python 和示意 `devtool` 命令只是可选起点，不能假定项目中已经存在或已安装。真实封装时再确认输入、输出、退出码、超时、日志、清理行为及板端副作用。

### 3.5 板端验证与模拟板端验证

第 5 步验证已集成版本的完整业务路径。先按验收要求选择真实板端、当前开发环境中的模拟运行，或两者结合。环境准备应在需求对齐和开发期间提前完成，交叉审查后再对最终候选版本执行场景验证。ADB 连通、程序可启动或编译成功只是前置检查。

真实板端路径：

1. 确认板卡 ID、CPU 架构、系统或固件版本、SDK 与依赖、设备访问权限，以及服务启停和恢复方法。
2. 使用板卡实际支持的 ADB、SSH 或串口连接。ADB 不是所有嵌入式系统的必备接口；多设备时显式选择目标，记录连接方式和设备身份。
3. 按项目已授权流程部署与候选源码一致的二进制、配置和依赖，记录构建与产物身份，确认板上实际运行的版本。
4. 从真实测试入口注入输入，沿驱动或总线、协议处理、业务服务、IPC、客户端回调或 HMI 检查结果。根据需求覆盖正常、边界、异常、重连和停机路径。
5. 采集适用的 DLT、logcat、串口日志、进程状态、崩溃信息和资源指标，对照预先确认的验收判据。结束后停止测试、清理测试数据、恢复服务并释放设备占用。

模拟板端路径：

1. 在当前开发环境运行目标模块的 host 构建、已有模拟器或项目支持的虚拟运行环境。容器用于组织环境和依赖；模拟器是否支持目标 SoC、外设及系统需单独确认。
2. 保留本次需验证的业务实现、协议解析、状态机和模块连接；在明确的硬件边界使用 mock、stub、虚拟总线或日志回放，并记录哪些组件真实运行、哪些被替代。
3. 使用与板端相同的需求和场景编号执行输入到输出的集成路径，检查过滤、取消、超时、重连等适用行为。只有单个函数的 mock 单测仍归第 3 步自测。
4. 输出模拟方式、测试数据或回放版本、日志、结果和限制。真实驱动、CAN 物理链路、硬件中断、板端调度时序及性能等未覆盖部分列为待板端验证项。

例如订阅过滤：板端从测试 CAN 输入进入协议解析、VehicleService 和订阅客户端，检查回调；模拟时在约定边界回放 CAN 帧或信号，运行实际服务及测试客户端，检查同一组场景。若从解码后的信号注入，则 CAN 驱动和解码链路不在这次模拟覆盖内。

每项验收记录必需环境与实际环境、源码和二进制身份、输入、预期与实际结果、命令、退出码和日志。模拟范围可单独判 PASS；若必需板端验收未执行，整项任务保留 BLOCKED 或待板端验证，已知失败继续保留。缺板卡时可以推进允许模拟的部分，但不能静默改变验收环境。

板端或模拟验证失败都返回原切片的 Loop。修复后重跑相关自测、受影响部分的独立审查以及对应场景，使用同一修复预算。详细操作写在模板 `docs/usage.md` 第 5 步，任务单与状态记录填写实际环境和证据。

## 4 v1 之后提出的四项细化

以下是助手于 10 月 12 日复查后的建议，**不是已全部实施的修改清单**。v1 已有部分基础规则，仍需决定是否及如何补齐。

### 4.1 验收标准必须有可观察判据

建议每条验收写明：前置条件与输入 → 可观察的预期结果 → 判断依据 → 必需验证环境。

例如“取消订阅正常”不够明确：需要区分禁止启动新回调、等待已开始回调完成，以及取消接口返回后能否释放关联对象。具体语义必须由真实需求决定。实现和测试使用相同误解时，也可能一起通过，因而不能只看测试是否绿灯。

建议落点：现有任务单的验收字段，不必为了这点新增一份文件。

### 4.2 Reviewer 发现应有关闭规则

- 确认缺陷：修复、复测，并由独立审查确认原问题关闭。
- 误报或不适用：记录理由与依据，不能直接忽略。
- 非阻断优化：明确标记，不要求所有建议都实施。
- 需求解释或风险接受争议：交给用户决定。

未解决的阻断项不能宣布 PASS。Reviewer 不是永远正确，编码者也不能凭主观信心驳回。

建议落点：Reviewer 角色和任务单审查结果。

### 4.3 修复轮数应有具体计数边界

建议把“一轮”定义为：基于一批已记录反馈进行修改，再执行验证；若根据新验证失败继续修改，就进入下一轮。

跨切片修改要记录受影响切片与预算归属，不得把问题转移到另一任务来清零。三轮共享预算已在 v1 中存在；需要补的是更具体、可审计的操作记录和边界。

### 4.4 人工 Review 反馈也应返回闭环

- 原需求没做对：回到对应实现，更新自测、独立审查和板端或模拟板端验证证据。
- 新增需求或改变取舍：先更新 Spec/CONTEXT、验收、范围和预算，再继续开发。

不能人工改完代码却不重验，也不能把新增需求混作原缺陷处理。

## 5 复杂资料输入的详细建议

以下是 10 月 13 日已给出的主要方案。用户现在希望接续该话题，但尚未提供具体项目材料来验证落地，也未最终确定所有文件和字段。

总体方法：**全局整理资料，按模块深入分析，按开发增量确认。** 不要求一次性理解完整个大项目，但当前准备实现的部分必须有足够明确的依据、架构影响和验收。

### 5.1 先建立资料清单和阅读覆盖

需求文档、架构图、协议、Excel、会议结论、历史决策和代码都可以作为输入。每份材料应记录：

- 来源与版本。
- 适用模块、车型或软件版本。
- 状态，例如已确认、草案、历史参考。
- 原文定位，例如文件、章节、页码、工作表或代码位置。
- 阅读状态，包括已读、未读、无法解析和需要人工核对的部分。

Agent 不能只提取文字就声称完整读懂架构图箭头或 Excel 合并单元格。摘要只做导航，关键约束仍须能追溯原文，不要一开始把所有材料压成一页摘要。

### 5.2 将要求拆成可追溯需求

为独立、可验证的要求分配稳定编号，例如 REQ-001。每条至少说明：

- 具体行为、触发条件、输入与输出。
- 正常、异常与边界场景。
- 相关模块、接口与依赖。
- 性能、资源、时序与兼容约束。
- 来源、未决问题、验收方式。

必须区分四类陈述：原文明确要求、现有代码事实、分析推断、设计建议。推断和建议不能自动升级为已确认需求。记录需要得到确认的假设，而不是藏进总结。

### 5.3 对照现有架构和目标变化

沿调用链、数据流与生命周期检查：

- 进程与线程分工。
- 数据的创建者、持有者、释放者及传递方式。
- 接口、状态机和配置的变更。
- 对其他模块、旧客户端、旧协议的影响。
- 初始化、退出、取消、超时、重试与重连。
- 性能和资源约束是否仍能满足。

输出必须区分“当前实际代码”“设计文档描述”“本次目标状态”。不默认代码正确，也不默认文档最新；三者不一致时列出差异和影响。

### 5.4 在需求阶段使用只读并行分析

不必等到编码才使用 subagent。复杂材料可按需分工：

- 需求分析：行为、场景、验收和来源。
- 架构分析：边界、依赖、职责和变化范围。
- 接口分析：协议、字段、兼容和生命周期。
- 验证分析：从需求独立提出测试、判据与可观测性缺口。

这些是可选方向，不是每次都必须启动四个角色。各方向共享来源清单与编号规则，由主 Agent 维护统一需求基线、汇总冲突并进行跨模块检查，避免各自写出互相矛盾的版本。

本阶段的依赖关系可以是：定位资料与范围 → 按需并行分析 → 汇总与跨模块检查 → 提交关键待决问题 → 更新基线。每项工作都要有输入、输出和依赖，不只是把长文分给多个 Agent。

### 5.5 用需求对齐 Loop 推进而非反复生成长文

一轮建议包括：

1. 展示本轮新增理解及依据。
2. 列出冲突、缺失条件和会改变方案的问题。
3. 用户回答关键问题。
4. 更新需求、决策与受影响验收。
5. 检查当前开发增量是否还有阻塞项。

可以每轮集中问 3–5 个高影响问题，说明依据、影响和可选答案；这是沟通建议，不是硬上限。资料或代码能回答的内容先查证，不把调查工作全部转成向用户提问。

问题分级：

- 必须先决定：影响公共接口、架构、安全、不可逆变化或正确性判断。
- 可记录假设后推进：局部、低风险、易回退，且不改变验收。
- 暂不涉及：后续功能问题，不阻塞当前增量。

**需求对齐的讨论轮次和实现后的三轮修复预算不是同一概念。** 不能直接把“三轮修复”机械套到资料澄清上；需求对齐的退出条件以当前增量是否可实施、关键问题是否已解决为准。

### 5.6 冲突不能由 Agent 静默裁决

典型例子：消息不得丢失、生产者不得阻塞、队列容量固定。需要继续确认突发量、消费速度、调度延迟和溢出策略；若条件下不可同时成立，应说明冲突、选项和代价，由用户决定，不能默默选择“满了丢旧消息”。

文档冲突也不能单凭修改日期较新就覆盖旧接口契约。需要明确适用范围和被认可的依据优先级。

### 5.7 当前增量的开工门槛

当前要实现的部分应能回答：

- 做什么、不做什么？
- 依据是什么，哪些仍是假设？
- 影响哪些模块、接口和架构约束？
- 关键冲突由谁确认、如何解决？
- 用什么可观察结果验收，必须在哪种环境验证？

未解决项应明确阻塞哪些任务。无关部分已明确时可以继续，不因为一个模块待决就停住所有工作，也不因为摘要写完就宣布分析完成。

### 5.8 变化只更新受影响部分

后续需求变化先分析：变化内容 → 受影响需求和决策 → 受影响实现 → 受影响测试与证据。更新相应基线和验收，不每次重新总结所有资料，也不沿用已失效的验证结论。

## 6 当前尚未决定的落地问题

这些是下一步需要讨论或通过真实材料确定的问题，不是已约定的新需求。

1. **先选哪个真实任务试用？** 新模块、新需求或架构变化均可；需明确当前增量和不做的范围。
2. **有哪些实际材料？** 存放位置、格式、规模、版本、适用产品与已知冲突；必要时由用户重新上传。
3. **哪类材料具有决定权？** 如何处理 PRD、接口协议、设计图、会议结论和当前代码之间的矛盾；哪些取舍必须由用户确认。
4. **如何组织最小产物？** 哪些内容放进现有任务单或 Spec/CONTEXT，哪些确实需要独立索引、需求记录、决策记录；具体目录、格式、编号方式尚未最终定案。
5. **怎样分块仍保持跨模块完整性？** 如何划分分析任务、维护共同来源和稳定编号、追踪阅读覆盖、做汇合复核与版本更新。
6. **怎样评估需求阶段完成质量？** 除阅读覆盖，还需要来源可追溯、冲突闭合、验收可观察、影响范围可解释；具体门槛由真实任务决定。
7. **落到哪个开发工具？** 项目可移植文档先于平台特有自动化；若要接入 Codex、Claude 或 Pi，应确认实际版本、工具和扩展，而非假定角色文件会自动执行。
8. **是否继续把上述建议写入模板？** 本次已将板端与模拟板端验证适配写入 v1.1；第 4、5 节的其余建议尚未全部落地，后续按真实任务决定。

建议接续顺序：先确认一个真实增量与材料入口 → 给出最小需求输入产物及协作方案 → 用少量真实材料走通一轮 → 根据暴露的问题修订模板。不要直接堆更多角色、目录或框架。

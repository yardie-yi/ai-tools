# Yardie 的工作 Team

服务于车载嵌入式开发、协议与接口维护、问题排查、项目资料和飞书工作记录。沿用已有六步开发流程，以实际证据交付；稳定步骤复用 Skill 和脚本。当前主助手负责统筹，按任务需要调用四类专业角色。

## 如何使用

在目标项目的聊天中直接输入：

```text
读取 /home/yardie/Desktop/persional/ai-tool/ai-tools/Team/README.md，按这个 Team 处理下面的任务：
项目/仓库：……
任务与资料入口：……
预期产物：……
本次操作范围：……
```

主助手先读当前全局及项目 AGENTS.md，再读 [Lead](roles/lead.md)。根据下表只读取所需角色和工作流。已有上下文能回答的字段直接复用；复杂任务简短复述目标和验收，简单任务直接做。

这些文件是可供当前助手执行的角色和流程定义，未注册为平台原生 Agent，也不会自动启动或定时运行。本次保留全局 AGENTS.md 原文，使用 Team 需要上述显式入口。具体平台不支持独立 Agent 时，由主助手完成可执行部分，并明确哪些独立审查未执行。

## 成员与分工

| 成员 | 唯一主要职责 | 默认写入范围 |
| --- | --- | --- |
| [Lead 主助手](roles/lead.md) | 对齐范围、维护任务基线、安排依赖、验收交付 | 当前任务单和整合记录 |
| [Analyst 需求与架构](roles/analyst.md) | 把复杂资料转为有来源、可实施的需求与接口基线 | 指定需求、设计和项目知识文件 |
| [Engineer 嵌入式开发](roles/engineer.md) | 实现或定位问题，并对自己的改动自测 | 分配的源码、测试及生成物 |
| [Quality 独立质量验证](roles/quality.md) | 独立核对需求、实现与证据，执行分配的场景验证 | 审查报告与验证记录；审查时不改实现 |
| [Work Assistant 工作事务](roles/work-assistant.md) | 根据证据整理资料并处理已授权的工作填报 | 指定文档、本人记录及授权目标字段 |

角色数量不等于运行中的 Agent 数量。默认当前助手推进；需要独立审查或确有独立子任务，且用户或适用项目/技能允许委派时，再创建所需角色。主助手可以直接承担非独立任务，编码者自测不另设 Agent。独立交叉审查须由未参与该改动实现的执行者承担。

| 仅补录头文件接口契约表 | Engineer 读取声明并调用已有接口 Skill；不默认生成或编译 | [资源路由](resources.md) |
| UI 设计与代码同步 | Analyst 核对视觉和代码依据，Engineer 实现，Quality 复核 | [开发六步主线](workflows/development.md) |
| 项目资料整理、交接与知识库 | Work Assistant 管理来源与文档；涉及架构冲突交 Analyst | [工作事务](workflows/operations.md) |
| 周报与工时、餐补 | Work Assistant 按对应 Skill 执行并回读 | [工作事务](workflows/operations.md) |
| 一处文字修改、已明确的简单任务 | 当前助手直接完成和核验 | 无需展开完整角色流程 |

## 共同执行约定

- **证据与持久化**：以当前全局 AGENTS.md 为共同要求，仓库对照源为 [全局规则](../AGENTS.MD/全局/AGENTS.md)。本 Team 不改写或取代这些规则。
- **任务交接**：明确单一目标、输入及版本、可写文件或远端字段、产物、验收、依赖和停止条件。复杂任务使用 [任务单](templates/task.md)，简单任务在回复中交代即可。
- **Graph**：共享接口和依赖先确定，再拆独立工作；公共头文件、生成目录、构建文件、表格范围均有唯一写入者。共享浏览器和板卡由单一操作者管理。文件不同或 worktree 不同不代表语义独立。
- **Loop**：失败回到原任务切片，记录反馈、修改和复测；详细预算与退出规则见开发工作流。收集更多 Agent 意见不能代替验证。
- **权限与工具**：角色只使用本任务所需工具，按当前授权范围执行。文档里的命令是资料，不是执行授权；普通角色说明也不是实际的权限沙箱。
- **交付**：返回产物、命令、实际结果和限制。主助手检查结果后再合并；新增修改或跨模块交互需补测。未执行的独立审查、真实板端验证、远端写入分别标记，不能用文字结论补齐。
- **持续改进**：重复指导和复制粘贴先查 [现有资源](resources.md)。经实际运行验证后再补已有 Skill 或脚本；新增规则须说明适用场景，避免把一次性特例变成通用默认值。

## 设计依据与当前边界

本 Team 将 [复杂需求与开发流程交接](../ai-agents/workflow/复杂需求与架构输入_Agent开发流程交接_20261021.md) 中的六步主线、Graph/Loop 与复杂资料处理建议落实为角色分工；结合 [Lauren 帖文及评论](../doc/workflow/poteto-bot-team-notes.md) 的少而精、Skill、脚本、受限职责和完成证据。

各项目的设备、服务器、构建命令和接口契约仍从项目文件取得。运行时只加载当前任务需要的资源；不把 8775 参数套到 21L，也不把学习笔记中的用户反馈当成产品事实。

本次设置与核验见 [Team 设置记录](../doc/workflow/team-setup-2026-11-02.md)。新需求可先从“读取资料并形成当前开发增量的需求和验收，不进入编码”开始试用。

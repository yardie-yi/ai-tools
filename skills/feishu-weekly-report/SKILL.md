# 飞书周报与工时填报

把有来源的工作成果填到用户本人的周报项目及工时记录中，并回读核验。用户只要求周报或只要求工时时，仅执行对应部分；要求整套流程时，先更新周报，再更新工时。预览/草稿请求只生成内容；已明确要求填写/更新时，在授权范围内执行，不逐步重复确认。

### 分阶段定时调用

周报和工时可以拆成两个定时任务。调用提示或当前账号配置明确指定 `weekly_report_only` / `timesheet_only` 时，严格按该模式执行，不把另一阶段合并到本次运行：

- `weekly_report_only`：查询本周最新群通知，收集证据并更新周报；完成周报回读核验后结束。
- `timesheet_only`：核对本周周期，读取本周已填写的周报及其他有效证据，仅更新工时表；不改动周报。群通知仅用于确认本周周报目标和周期，不要求本次再次写周报。

具体星期和时间属于账号偏好，保存在个人配置和对应自动任务中；Skill 不设置所有账号通用的固定执行日。手动请求同时更新两项时，仍按“周报 → 工时”顺序执行。

## 1. 建立账号与配置

首次调用，或尚无当前账号配置时，集中询问两个入口：

1. **工作周报在哪里获取？** 可以提供周报链接，或说明哪个飞书群会发布周报填写消息。
2. **工时填报链接是什么？** 请用户提供真实页面链接。

当前会话已经提供的答案直接复用，只询问缺失项。同名群先搜索，列出创建时间、群主或近期消息供用户选择，保存选中的 `chat_id`。不能根据群名相同自动换群。仅提供周报链接时可以完成当次填写；要支持后续定时调用，还需取得并保存发布周报消息的群 `chat_id`。

首次配置、CLI 缺失、登录或权限异常时，读取 [安装、授权与配置](references/setup.md)。安装完成并取得有效的 **user 身份** 后，确认登录姓名及 `open_id`，按账号保存配置。现有账号有效时不重复登录，也不创建新应用覆盖已有配置。

**飞书业务读写全部使用飞书 CLI（`lark-cli`）。** 授权所需的用户扫码或官方授权页面由用户完成，Agent 继续使用 CLI 完成后续步骤。

## 2. 确认本期与收集证据

- **每次调用都先重新查询已配置群聊中的最新周报填写消息，包括手动调用、重复调用和定时调用。** 按消息发送时间倒序检查含周报填写入口的消息，解析其中的真实文档链接；以最新一条有效填写消息为本轮目标。保存的上次文档链接只用于比较和去重，不能直接复用为本轮目标。
- 只有催填文字而没有填写入口的消息不算有效目标。转发、重复发布或更正消息以发送时间最新且链接可访问的一条为准，并核对文档标题和正文日期。若最新消息的周期与用户指定周期或当前日期明显冲突，停止写入并说明冲突，不能静默回退到旧链接。
- 尚未配置群、群不可访问或权限不足时，提示用户补充群信息或完成授权；不能为维持定时任务成功状态而填写缓存的历史周报。
- 用实际日期对齐周报和工时填报周期，不直接把文档的 `Week N` 当作工时系统的第 N 周。周期冲突无法判断时，询问用户。
- 按当前运行环境的用户时区确定日期；用户未指定时采用其环境时区，不依赖服务器时区。
- 每次收集本地记录前，读取并执行[本地工作记录的发现与核实](references/local-work-records.md)。**最低必查 Codex、Pi、Claude/Claude Code 的本期对话记录，以及本期相关 Git 仓库的提交、分支、工作树修改和文档产出**；再覆盖本机发现的其他 AI/Agent、IDE、笔记、任务、排查测试、交付与协作记录。产品名不是白名单，某项不存在、不可访问或本期无记录时也要留下检查状态，不能静默跳过。
- 先建立来源清单，再按本期事件时间定向读取；核对本人贡献、实际结果及跨来源重复项。重复调用使用增量索引，并合并本期完整证据，保持填报简洁；来源不可访问或无法解析时如实记录缺口。
- 从当前飞书用户本人发送的本期消息开始，必要时补读关联群聊、私聊及讨论上下文。指定发送人、时间范围，完整分页；已知群只在该群内查找周报消息。
- 将私人闲聊、学习娱乐、工具安装等与项目无关的内容排除。读取会话文本与工作产物，不扫描认证文件、环境密钥或账号密码；输出和周报均不包含这些信息。

整理内部证据表：`项目候选 / 工作事项 / 最终状态 / 日期 / 来源定位 / 待验证内容`。合并同一事项的多次讨论，以最后有效状态为准；回退、中断或只提出方案的内容不能记为已交付。区分编译通过、主机测试通过、板端联调通过和根因确认。

### 填写内容的简洁程度

- 证据保留在内部整理结果中，实际填写只概括主要工作、成果和当前状态。同一事项的分析、修改和验证合并表达，省略过程流水账、日志细节、文件路径、函数名及提交编号；确需识别问题时保留问题编号。
- 周报默认每个项目 1–3 条，每条一句，通常约 20–50 字；事项少时一条即可。沿用模板要求和原有简洁语气，重要的独立成果可以适当增加。
- 工时工作简述比周报更短：每个项目 1–2 句，通常合计约 40–80 字，概括主要投入即可，无需复制完整周报或重复占比。
- 精简后仍保留影响交付的阻塞和“分析中、待验证”等关键状态，不能把排查或方案写成已解决。风险和后续动作已有专栏时放入对应栏，避免多处重复。

示例：“分析仪表 I2C 通信异常，梳理重试与恢复方案，待板端验证。”字数是参考，不为凑字数添加内容，也不为压缩而遗漏重要事实。

完成标准：每条拟填事项都有可追溯来源、正确周期和明确的完成状态。不可访问的记录源应如实说明，继续利用其余可访问来源。

## 3. 对应周报项目并更新

读取周报的项目、负责人、用户本人行、进展及风险/下周计划。CLI 命令及局部写入方法见 [CLI 操作与核验](references/cli-workflow.md)。

- 使用登录 `open_id` 确认本人，姓名只辅助展示。
- 优先沿用已确认的项目别名与映射。项目相近但无法唯一对应时，提醒用户并列出“工作事项 → 候选项目”，请其选择；等待期间可继续处理已明确的项目。
- 用户确认后的映射保存到当前账号配置。已确认“9868 仪表属于五菱F610M”之类的关系可以复用，但不能扩展到所有账号和项目。
- 周报中没有对应项目时，查阅本期周报结构及工时项目目录；找到唯一项目后按现有格式添加本人内容。新增行涉及合并单元格或负责人不明确时，先解决定位问题，再写入。
- 根据原有表格语气写简洁的工作内容。保留原有工时、完成百分比及未完成状态；新增事项不凭空补工时，也不把完成百分比当作工时占比。
- 只局部修改本人对应的进展、风险、后续计划及相关待办，保留其他人、@人、附件、表格结构和未完成复选框。

每次文档写入后重新 fetch 受影响范围。结构发生变化后重新获取 block ID；发现并发改动时重新合并，不覆盖他人新内容。

## 4. 更新每周工时

解析用户的工时页面，读取填报说明、底层表、字段类型、本人已有记录、项目来源及锁定状态。使用**工时表的实际项目名称**，允许与周报简称不同。

`timesheet_only` 定时运行时，优先读取本周已经确认的周报内容作为项目与工作简述依据，再用本地及飞书证据补充核验。工时页面尚未开放或记录仍锁定时，不提前写入、不解除锁定；准确报告需用户处理的状态。

### 查找项目与复用记录

1. 先在本人已有工时记录中匹配项目，按 `record_id` 更新，保留历史填报。
2. 工作事项没有对应的已有工时行时，**自行查询真实项目目录**：先查项目选项、关联项目表或页面引用的 Base；再按正式名称、简称及已确认别名搜索。核对项目有效状态、所属业务及可填报范围。
3. 找到唯一的既有项目后，自动添加该项目的本人填报行，填写正确的项目关联、用户、周期等必填字段，再写工作内容及占比。这里是添加填报记录，不是新建项目、修改选项定义或扩大权限。
4. 多个候选无法消歧时，请用户确认项目；遍历可访问项目目录后仍无对应项，报告缺失，不以“其他”项目、无关项目或虚构名称凑数。

### 工时占比

- 优先保留本期已填写且符合规则的占比，采用用户提供的实际分配。实际投入时长与比例可按表中单位换算，完成率不能参与此换算。
- 占比缺失时，请用户提供分配或允许根据工作记录估分。用户已明确允许“自行分配”时，直接按本期工作重心估分，写前简要告知分配及其估算性质；后续仅在配置明确记录该偏好时复用授权。
- 将估分分配给有证据的项目，遵循表的精度/舍入规则，累计等于页面要求的总量（本例为 100%）。对无本期工作的项目，不分配正工时来补足总数。
- 百分数字段按实际 schema 的数值约定写入；当前 Base percentage 字段 `0.6` 表示 `60%`，以读回结果核实。
- 只修改目标字段，不改历史、公式、锁定或自动编号。锁定记录不能通过解除锁定绕过，告知用户需要业务解锁。

先完成本轮相关变更，再统一回读。异步写入未及时可见时短暂等待后有界重读；不能因首次读回未更新而重复创建记录。

## 5. 完成核验

只有以下条件成立，才报告对应部分已完成：

- 周报本人项目内容与拟写证据一致，其他人及原有结构保持完整。
- 工时目标记录确实存在，项目、用户和周期正确，工作简述及占比与计划一致。
- 无重复填报；如表内有“累计有效工时/填报率”等公式，读回结果满足页面规则。只有本地求和为 100%，不能替代系统的有效工时核验。
- 有缺少项目、权限、锁定、周期或归属问题时，准确区分已完成部分与未完成部分，不将部分写入报告为全量成功。

最终简述周报/工时链接、实际更新项目及占比；估分注明按记录分配。不要把聊天原文、私密信息和长篇分析作为填报内容发布。

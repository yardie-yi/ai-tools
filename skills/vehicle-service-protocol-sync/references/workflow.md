## 源请求规范化

源表的数据表头包括：

`序号`、`接口名（最终接口名会根据上下行添加前缀get\set）`、`接口说明`、`上下行（上行-接收数据、下行-发送数据）`、`通信方向`、`GID/CAN ID`、`SID/Signal Name`、`填写人`、`填表日期`、`合入日期（由vehicle-server填写）`。

忽略说明行和完全空白行。具有接口名、通信方向且合入日期为空的请求视为待合入。保持源表合入日期不变。根据源请求身份、解析后的类型及外部映射判断是否已合入，也须识别因同名冲突而另命名的接口。

读取源表中标注 `QNX与MCU私有协议` 和 `QNX与ANDROID私有协议` 的实际链接，包括普通 CSV 读取可能遗漏的富文本超链接。根据链接资源类型使用相应飞书文档、知识库或多维表格技能。仅有文档显示标题或“待定”等占位文字，不能作为协议定义。

通信方向按下表转换：

| 源表方向 | 目标 `数据方向` | 接口 `type` |
| --- | --- | --- |
| `MCU->QNX` | `MCU→CLU` | `field` |
| `QNX->MCU` | `CLU→MCU` | `method` |
| `ANDROID->QNX` | `IVI→CLU` | `field` |
| `QNX->ANDROID` | `CLU→IVI` | `method` |
| `CANUP` | `CAN_UP` | `field` |
| `CANDOWN` | `CAN_DOWN` | `method` |
| `QNX->QNX` | `CLU→CLU` | 发送端 `method`，接收端 `field` |

对于 `QNX->QNX`，使用唯一的反斜杠拆分源接口名。前者是发送方法，映射到后者的接收字段；接收字段不能再新增独立的 Mapping 生产者行。分隔符缺失、多余或含义不清时，将请求列为待解决项。

## 接口说明原文同步

源表每条待合入请求的 `接口说明` 单元格原文，直接写入 `Interface定义表.desc` 和该请求对应的 `VehicleMapping.备注`。两处文本必须与源单元格逐字符相等，包括前后空格、换行、标点、大小写及原有错别字；不执行 trim、改写、摘要、纠错、翻译或添加前后缀。源说明为空时两处留空，不根据接口名补写说明。CSV 引号与转义仅用于序列化，比较时使用解析后的单元格文本。

每个本轮候选接口均保留源行号与原始说明。QNX→QNX 拆成发送和接收接口时，两条 Interface 的 desc 均复制同一源说明，只有发送方法对应的 Mapping 备注也复制该说明；接收字段不另建 Mapping。

协议来源、版本、方向、帧 ID、另命名原因、原请求名与新旧契约差异写入本轮独立同步清单，不能追加到 desc 或备注。清单记录“源行/源名→最终接口名→类型及映射→协议依据/冲突原因”，供回读、交付及重复执行查重使用；再次执行结合源身份、类型和外部映射复核，不依赖 desc/备注承载这些元数据。

已匹配的本轮待合入请求也检查两处说明：契约和映射相同时只同步不一致的 desc/备注，不新增重复接口，不改其他字段。多条源请求映射到同一接口且说明不同、或无法唯一定位源请求时，将冲突列为待解决项，不任意选择一份说明覆盖。没有对应本轮请求的历史记录保持原样。

写前候选校验及写后回读均断言 `desc == 源接口说明`、`备注 == 源接口说明`；按解析后的单元格文本比较，不将换行或空白规范化后再比较。导出后对 CSV/XLSX 的这两列继续核对原文，不能只验证非空或关键词。

## Interface定义表填写

- 保留 `server=Vehicle` 和现有 `server_id`，先核对当前值。
- 根据权威依据确定请求的 `type` 和 `data_type`，再判断能否复用已有接口。新请求与已有契约冲突时，保留已有接口的名称、类型、数据类型、GID、SID 和业务消息 ID。
- 新 CAN 接口的 `data_type` 使用 `scripts/resolve_can_signal.py` 返回的实际 C++ 基础成员类型。生成器会规范化支持的类型别名；不能仅根据描述将数值信号改成枚举。
- 根据下述业务分类规则选择类别及其 GID，再在该 GID 内分配最小的未使用正 SID。已有接口的类别、GID、SID 和消息 ID 保持不变。
- 根据目标当前规则 `0x0B<server_id><GID><SID>` 计算业务消息 ID，各部分占一个字节，并检查整个接口表中的唯一性。
- 新增非 CAN 接口须使用已有权威 API 声明、类型或明确协议定义；源请求表本身不能证明载荷类型。
- 仅在目标分组布局需要时新增分组标题行。分组标题不是接口，除标题格外其他单元格留空。

### 业务分类与分组排版

先读取 Interface 表的全部分类标题、分组边界及各组现有 GID，再依据源表的 `接口说明` 判断业务归属。接口名辅助理解；说明中的“实际信号含义”优先于名称或“近似状态”。分类判断只影响业务组织，不用于推断类型、枚举或协议布局。

- 优先复用语义合适的现有分类：电源状态用于电源/点火/休眠，车辆信息用于通用车辆状态，行程数据用于里程、行程时长、平均速度及行程能耗，进程间通信用于本地进程消息，多媒体用于媒体信息。CAN 是通信方式，不是业务类别。
- 现有类别过于宽泛时，可新增明确的业务类别，例如动力系统、胎压与胎温、灯光状态、底盘与行车安全、车门与舱盖、驾驶辅助、新能源与充放电。按本轮真实接口选择类别，不创建空组，不为每个接口单独建组；含义不明且影响分类时列为待解决项。
- 建立“源行→最终接口→类别→GID→目标行”清单，每个新增接口恰属一个类别。同类别保留源表相对顺序；再次执行复用已有类别和已合入记录。
- 复用分类时沿用其现有 GID；新增分类先核对工作簿规则及保留编号，未指定时分配未使用的正一字节 GID。类别、GID、业务消息 ID 必须一致；外部 CAN ID/私有帧 GID 与业务类别 GID 分别处理。
- 现有类别内的新增接口，物理插入到该组最后一条接口之后、下一组标题之前。按位置从下往上插入，防止早期插入改变后续锚点。新增类别接在现有分类之后，以独立标题行和连续数据块展示；不把所有新接口堆到最后一个类别下。
- 分组标题继承现有标题的合并范围、底色、字体、对齐和行高，只填分类名；数据行继承同类模板的字体、四边框、对齐和文本编号格式。长接口名及说明启用自动换行并调整行高，不改无关区域的列宽和风格。
- 插行后回读原行的值、平移后的公式与合并范围，保持已有业务 ID 不变。更新受插行影响的接口引用/下拉源范围，覆盖完整接口区。VehicleMapping 不插分类标题，按最终 Interface 顺序组织本轮新增映射并保留已有映射。

### 同名接口契约冲突

源接口名已存在时，比较 `type` 和 `data_type`。任一列不同，必须使用唯一新名称新增接口，保留原行及原 Mapping。基础类型别名按生成器的规范化规则比较，例如 `uint8` 和 `uint8_t` 等价；枚举和结构体名称仍表示不同类型。

新名称使用有含义的 CamelCase 命名，可在原名称后增加区分方向、角色或数据类型的后缀。检查其在已有记录及本轮候选行中的唯一性，为其分配独立的未使用业务 ID。Interface 和 VehicleMapping 均使用最终新名称；仅为需要该新接口的请求调整本地目标接口引用。

新行的 desc 和 Mapping 备注按“接口说明原文同步”规则填写。原请求名、已有契约、新契约及另命名原因记录在独立同步清单中。

重复执行时，先寻找已新增的独立接口，结合独立同步清单及源请求身份，核对最终接口名、类型、数据类型和映射；全部匹配时复用。仅匹配原接口名不能判定请求已经合入。

## Data_type定义表填写

类型选择、声明格式、枚举、结构体和字节数组的具体规则与写前联合校验见[数据类型与 Mapping 联合填写](data-types.md)，构造候选行前完整阅读。

CAN 基础类型无需新增类型定义。只有已有 vehicle-service 代码、当前类型表或明确协议文档中存在权威定义时，才新增枚举或结构体行。

枚举、平面结构体、`bytes[N]` 及末尾有界 `bytes` 成员须严格遵循 `VehicleMapping填写说明.md`。描述文字不能证明枚举编码、线值换算、边界或无效值。缺少权威依据时，写入前将该接口列为待解决项。

## VehicleMapping填写

- 从已验证的接口候选行复制 `interface`、`type` 和 `业务消息ID`。
- 对于 `CAN_UP` 和 `CAN_DOWN`，使用源 CAN ID 及工具返回的零基成员序号；字段布局、目标接口、载荷长度和约束规则留空。
- 对于 `CLU→CLU`，仅填写发送方法的 Mapping，将 `目标接口` 设为接收字段；帧信息和布局列留空。
- 私有协议的 `字段布局` 按下述链接文档流程确定。代码和已有目标行用于检查 API 兼容性，仍须查证链接协议文档。
- `字段布局` 和 `约束规则` 中每条配置独占单元格内一行，保留换行。

### 查证私有协议文档

| Mapping 方向 | 源表协议链接 |
| --- | --- |
| `MCU→CLU`、`CLU→MCU` | `QNX与MCU私有协议` |
| `CLU→IVI`、`IVI→CLU` | `QNX与ANDROID私有协议` |

每条私有协议 Mapping 都须打开对应源单元格链接，在文档中找到外部 `帧GID` 和 `帧SID` 同时匹配源请求的帧定义。按数值规范化十六进制和十进制写法，并匹配通信方向；其他链路或反方向的相同 GID/SID 不能证明该布局。匹配的是外部帧 ID，而非 Interface 表中的业务 GID/SID。

先区分有效业务字段、协议常量和保留字节。多个有效业务字段使用结构体 data_type，在 Data_type定义表逐项声明并在 Mapping 绑定真实成员；协议枚举即使目前只定义一个值，也保留为 API 成员，并用 allowed 约束已定义值。只有文档明确要求字节固定为某值时才写 const(...)。

SoundValue 等完整多字段类型的填写样例见[数据类型参考](data-types.md#本工作簿核对样例)。

用户明确要求修正本轮错误时，在原接口行和业务 ID 上更正类型，并同步类型表、Mapping、生成代码和契约表；这属于纠错，不按新请求的同名契约冲突另建接口。

完整读取匹配的帧定义，包括关联表、载荷字节位置、长度、端序、保留字段、常量、换算和无效值。按 `VehicleMapping填写说明.md` 将线字段绑定到 API 的 `value` 或真实结构体成员。执行记录中保留协议 URL、可获取的版本、帧章节、方向及 GID/SID，统一记录在独立同步清单中；VehicleMapping 的备注仅保留源接口说明原文。

链接缺失、无法访问、尚未确定，或无法唯一匹配方向和 GID/SID 时，逐项列出接口及缺少的依据。字节序、长度或字段含义无法确定时也应阻塞该项，等待依据明确后再改其已有在线行。禁止借用相似帧布局，或将缺失的有效参数冒充保留字节。

写入前检查：

- 接口名和业务消息 ID 唯一。
- 每个接口恰有一个 Mapping 生产者，`CLU→CLU` 的目标字段除外。
- 方向与 `field/method` 一致。
- 每个 CAN ID 对应头文件存在，信号精确匹配，解析类型与 API 基础类型一致。
- 私有布局符合仓库的字节覆盖、端序、变长尾部和约束规则。
- 每个同名类型冲突都有独立新名称、新业务 ID、独立同步清单中的冲突原因及匹配的 Mapping。
- 每个私有布局都可追溯到源表对应协议文档，且方向、帧 GID、帧 SID 精确匹配。

## 在线写入与导出

Interface 表按上述类别边界插行，VehicleMapping 与类型表使用数据末尾后的空白行。继承同类模板样式，以明确 A1 范围写入。回读每个新增类别的标题和首、中、末行，以及全部多行布局或约束单元格；检查类别连续、无空标题、GID 正确、原有分类未被新增数据混入。

写入前立即记录版本，验证后再记录版本。写入前发现版本意外变化时，重新读取目标表并重新计算待写入差异。

使用 `lark-cli sheets +workbook-export` 导出：整簿一次 `xlsx`，每张必需业务表各一次 `csv`；子表 ID 使用本轮 `+workbook-info` 的返回值。文件参数须相对 CLI 当前目录，因此在临时导出目录运行并使用相对输出路径。CSV 均从目标协议工作簿导出。

## 生成与校验

在 `vehicle-service/doc/` 执行；两个 Python 命令均可用时优先 `python3`：

```sh
python3 gen_libapi.py
python3 gen_libapi.py --check
python3 test_business.py
```

使用默认文件名、CAN 目录和输出目录。仅当仓库说明或用户明确要求时使用自定义参数。命令无输出但退出码为 0 时视为成功，非 0 为失败。

`test_business.py` 是 CSV/XLSX 同步检查，即使生成和 `--check` 通过，也须执行。

## 服务器编译

使用已认证的服务器会话或用户提供的 SSH 目标。确认该会话中存在 `embedded-software/autoai-services/build-script/env_setup.sh`，再在同一 shell 中执行，确保加载的环境保持有效：

```sh
cd embedded-software/autoai-services/build-script && source env_setup.sh sa8775 && make vehicle-service
```

`git pull`、复制文件、部署、启用测试构建或修改 CMake 选项须另有授权。必须实际执行服务器编译。

## 编译后接口契约同步

服务器 sa8775 编译命令退出码为 0 后，调用 `vehicle-interface-api` 技能，按其说明执行接口契约同步；编译失败时不执行此阶段。

传入以下固定参数：

- 头文件：`embedded-software/autoai-services/vehicle-service/libvehicleapi/include/vehicleapi.h`
- 飞书多维表格接口契约表：`https://navinfo.feishu.cn/base/BChgbaVvhaskKUswBY3cgIZTn0d?table=tbl72rMWhuDNQ3b6&view=vewc7rJMLW&hideSidebar=1&hideHeader=1`
- Base token：`BChgbaVvhaskKUswBY3cgIZTn0d`；数据表 ID：`tbl72rMWhuDNQ3b6`；视图 ID：`vewc7rJMLW`。

将头文件路径解析为当前仓库中的绝对路径：工作区根目录包含 `app/` 时，上述路径位于 `app/` 下；工作目录已在 `app/` 下时直接解析。核对该文件确为本轮生成且已成功编译的头文件，不使用旧安装副本。

执行前完整读取 `vehicle-interface-api/SKILL.md` 及其要求的参考文档，遵循该技能的字段映射、写入范围和回读校验规则，不自行假设多维表格字段或覆盖策略。技能不可用时报告缺少依赖，请用户提供或安装后再继续，不用临时实现替代。同步成功后报告该技能的新增、更新、跳过数量及校验结果；同步失败不回滚已成功的协议表、代码生成或编译阶段，并明确完整流程尚未完成。

# 车辆服务协议同步

将协议表同步、导出、生成和编译作为一个逐阶段校验的流程执行。检查或修改项目数据前，先阅读 [工作流说明](references/workflow.md)。

填写或核查 `data_type`、类型定义、字段布局前，必须完整阅读[数据类型与 Mapping 联合填写](references/data-types.md)，按其中规则对三张候选表做写前联合校验。

飞书表格的读取、写入、版本查询和导出均使用 `lark-sheets` 技能，并按其要求读取认证、写入、导出和回读校验的参考文档。

## 服务器连接

- 默认 SSH 入口：`yiwanming@172.19.160.73`。
- 用户提供的登录密码为恰好一个 ASCII 空格（U+0020），即字符串 `" "`；不是空字符串。通过 SSH 密码提示输入该字符后回车，保留空格，不执行 trim。
- 登录后确认本轮工作区对应的服务器项目路径及 `embedded-software/autoai-services/build-script/env_setup.sh`，再执行编译。

## 完成条件

只有以下条件全部满足，才能报告任务完成：

1. 每个符合合入条件的源表请求都在目标工作簿中唯一对应，或已逐项列出阻塞原因及缺少的权威信息。
2. 目标工作簿中的 `Interface定义表`、`Data_type定义表` 和 `VehicleMapping` 均通过写后回读校验。
3. 仓库的指定路径包含同步后的 1 个 XLSX 和 3 个 CSV 文件。
4. `gen_libapi.py`、`gen_libapi.py --check` 和 `test_business.py` 均成功退出。
5. 服务器上的 sa8775 编译命令成功退出。
6. 编译成功后，已按工作流说明调用 `vehicle-interface-api`，使用指定头文件完成指定飞书多维表格接口契约表的同步和该技能要求的校验。

仅部分阶段成功时，报告最后通过的阶段、失败的具体命令或缺少的输入。

## 执行约束

- 用户明确要求执行本技能时，授权范围包括指定目标工作簿的编辑、四个本地表格文件的替换、代码生成、编译，以及编译成功后通过 `vehicle-interface-api` 同步指定接口契约表；源请求表修改、提交、推送、部署及无关清理需另有授权。
- 首次写入飞书前，确认可用的服务器会话或主机，并确认远程构建目录存在。如果无法从当前会话或用户提供的配置中确定服务器入口，先获取该信息。
- 修改前记录目标工作簿版本和四个本地文件的哈希。导出文件先存放在临时目录，待四个文件齐全且可读后再替换。
- 保留无关的工作区改动。仅修改指定表格及生成代码输出，禁止重置、丢弃或覆盖其他文件。
- 私有协议按[有效字段与常量规则](references/workflow.md#查证私有协议文档)确定完整 API 类型；多字段载荷须保留所有有效成员，用户要求纠错时原位修正并重新执行后续阶段。
- 源表 `接收/发送数据` 中“接收”对应 `field`、“发送”对应 `method`，以 QNX 为视角，并与通信方向交叉校验；兼容旧“上行/下行”字段。
- 源表 `接口说明` 原封不动同步到 `Interface定义表.desc` 和 `VehicleMapping.备注`，写前及回读逐字符核对；协议来源、冲突说明另记独立同步清单，详见[原文同步规则](references/workflow.md#接口说明原文同步)。
- 使用源表、协议文档和仓库声明作为依据。缺少依据的字段保留为待解决项；不得从名称或描述推测私有协议的载荷布局、端序、保留字节、枚举值。

## 执行流程

表格只描述类型、字段布局、载荷长度和路由；业务值的判断由应用或对端负责。具体边界见[数据类型与 Mapping 联合填写](references/data-types.md)。

1. 根据指定文档定位仓库，完整阅读两份仓库 Markdown 说明。检查适用的 `AGENTS.md`，以及四个表格文件和生成文件的工作区状态。
2. 检查飞书访问权限、源和目标工作簿结构、目标当前版本及服务器连通性。每次执行均按工作表名称重新查询子表 ID。
3. 完整读取源表和目标三张业务表的已用区域，包括源表 `QNX与MCU私有协议`、`QNX与ANDROID私有协议` 单元格内的实际超链接。选取 `合入日期（由vehicle-server填写）` 为空的有效请求，按参考文档中的冲突规则比较接口名、类型、数据类型及映射，使重复执行不会重复新增。
4. 按[工作流说明](references/workflow.md)构造候选行，并根据源表接口说明确定业务类别和分组插入位置。使用 `scripts/resolve_can_signal.py` 解析 CAN 信号；私有协议先读取对应链路的协议文档，匹配方向及外部帧 GID/SID 后确定字段布局。同名接口发生类型或数据类型冲突时保留原接口，另命名新增并在独立同步清单中说明。写入前校验候选行、分类/GID、ID、类型、映射和协议依据。
5. 依据完整且确定时，将新增接口插入各自类别的数据末尾；现有分类不能准确表达业务时新增分类。按参考文档继承分组标题与数据行样式，保留已有记录、公式、合并单元格和工作表顺序。写前说明类别、新增数量及新增类别。
6. 按精确范围回读每个写入行，核对类别归属、名称、ID、方向、CAN 序号、类型、单元格内换行及重复项，并确认插行后的原记录和公式保持一致、目标版本较基线增加。
7. 将整个目标工作簿导出为 XLSX，将三张指定工作表分别导出为 CSV，先存入临时目录。确认四个文件均非空、CSV 表头符合生成器要求后，再成套替换仓库中的四个指定文件。
8. 在 `vehicle-service/doc/` 中按文档运行默认生成命令。依据生成器诊断修正在线表格，重新导出并重试，保持在线表和本地文件一致。连续三轮修正仍失败时，停止并报告剩余诊断。
9. 在已确认的服务器环境中执行 sa8775 构建命令。失败时保留完整退出状态及最后的错误段。服务器编译须实际执行。
10. 仅在服务器编译成功后，按[工作流说明中的接口契约同步](references/workflow.md#编译后接口契约同步)调用 `vehicle-interface-api`。先完整读取该技能及其要求的参考文档，再传入本轮生成的指定头文件和指定多维表格。缺少技能或同步失败时，保留前序结果并报告此阶段未完成。
11. 报告新增、跳过、阻塞的接口，目标修改前后版本，替换文件，脚本报告的生成文件，测试结果、服务器编译结果、接口契约同步结果及剩余缺口。

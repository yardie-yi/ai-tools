# UI 设计与代码同步

把 UI 设计页中的视觉事实转成可审查、可追踪的项目改动。开发工程师和项目代码决定页面职责、控件类型、控件名称、父子关系、状态及业务逻辑；设计页用于确定页面视觉结构、切图、坐标、尺寸和主题差异。不得把设计图层名称直接当成业务控件定义。

## 1. 准备 Browser Harness

查看设计链接前，先运行本 Skill 自带的 `scripts/bootstrap_browser_harness.py`。脚本路径必须相对于本 `SKILL.md` 解析。

- 已存在时复用现有 Browser Harness 和用户已登录的浏览器会话。
- 不存在时由脚本优先通过 `uv tool` 安装；没有 `uv` 时使用 `python -m pip --user`。安装后验证命令可用。
- 安装失败时报告实际命令和错误，不得声称已经检查设计页。
- 不得读取、打印或保存 Cookie、令牌、密码以及 `.env` 内容。

优先用 Browser Harness 获取 DOM、画布、设计属性、原始资源地址和截图。截图只用于理解和验证，不能代替原始切图。

## 2. 必须提供设计链接

用户没有提供明确的 UI 设计 URL 时，提醒其提供链接，并在分析仓库或修改文件前停止。只有项目名、截图或页面名不满足此条件。

收到链接后，在已登录会话中打开，并定位用户指定的准确页面或画板。若登录失效，让用户重新登录后重试同一链接。

## 3. Jev 可用时实际调用

运行本 Skill 自带的 `scripts/detect_jev.py`。脚本只检测 Jev，不负责安装。检测结果含 `cwd` 时，在该目录执行返回的命令。

Jev 可用时：

- 加载并遵循 `typesafe-ai` Skill，包括其要求读取的在线文档。
- 对已经观察到的设计和代码状态至少发起一次真实的 Jev/System One API 请求，用 Choice、Noul 或 Score 判断语义匹配、歧义或证据优先级。
- 坐标提取、哈希、XML 解析和文件修改使用确定性代码。Jev 不能替代这些检查。
- 记录实际模型标识、答案、概率或置信度，以及该结果影响的判断。仅启动本地服务不算调用 Jev。

Jev 不存在时跳过。Jev 已存在但因凭据、网络或服务配置失败时说明限制；除非用户要求 Jev 必须成功，否则继续完成确定性分析。

## 4. 判断工作模式

先检查目标页面在项目中是否已有可维护的 XML 或等价布局源码：

- **新项目模式**：目标页面尚无布局源码，需要从设计页生成候选页面、控件、资源和坐标。读取 [references/new-project.md](references/new-project.md) 并按其流程执行。
- **旧项目模式**：目标页面已有布局源码，需要同步现有控件、切图或局部结构。读取 [references/existing-project.md](references/existing-project.md) 并按其流程执行。

如果仓库中同时存在新旧页面，按页面分别选择模式。证据不足以判断目标 UI 引擎、布局文件或页面归属时，列出主要候选及证据，让用户确认后再修改；不要根据设计标题猜测代码位置。

## 5. 建立设计与工程证据

设计侧至少记录：设计 URL、页面或画板名、画布尺寸、图层或切图名、绝对坐标、尺寸、主题版本和原始资源地址。

工程侧按实际情况检查：

- UI 引擎、版本、XML schema、项目样例和命名规范；
- 页面 XML、布局或场景源码；
- 控件查找、初始化、显隐、位置、尺寸、主题和图片设置代码；
- 各分辨率与昼夜主题资源目录；
- 资源打包规则和可用的官方导出工具；
- 运行时覆盖 XML 属性的代码。

计算父容器偏移，区分设计绝对坐标、XML 父容器局部坐标和运行时坐标。文件名相同或视觉相似都不能单独证明映射。

整理 `设计元素 → 页面/候选控件/资源/代码 → 证据 → 拟执行操作` 映射。旧项目必须由现有 XML 和代码控件反向寻找设计元素；新项目的设计图层只能生成候选控件，不能自行定义业务含义。

## 6. 修改规则

- 严格执行用户要求的增、删、改、查或验证范围。
- 从设计服务下载原始资源，不得使用截图、缩略图、缩放图或重新编码图片。当多个切图同名时，不得仅按名称去重。
- 主题资源按项目现有昼夜机制分别保存和绑定。
- 如果运行时代码覆盖 XML 的位置、尺寸、显隐或图片，修改真正生效的值。
- XML 内嵌图片需校验解码格式、尺寸和哈希，并确认无关 XML 内容未变化。
- 只使用仓库已有且能够证明正确的工具生成专有 UI 二进制；无法执行时明确列出待导出产物。
- 除非用户明确要求，不新增车辆信号、业务判断或状态机逻辑。

## 7. 验证与报告

根据变更执行确定性验证：

- 解析修改后的 XML 或布局；
- 检查控件名称唯一、父子层级合法、代码查找可命中；
- 核对坐标、尺寸、主题映射、资源格式、像素尺寸和哈希；
- 检查差异只包含预期字段和文件；
- 有真实项目命令时运行布局生成、资源打包、测试或构建；
- 区分源码修改、UI 二进制导出、固件构建和目标设备验证的完成状态。

最终报告包含：工作模式、设计与工程映射、修改文件、人工确认记录（新项目）、验证证据、Jev 实际调用或跳过原因，以及仍待处理的导出、构建或设备验证事项。

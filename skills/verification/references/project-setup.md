# 项目入口与功能地图

当重复任务缺少可控运行环境或验证入口时，先补最短路径。保留现有技术栈与仓库约定；本文不要求迁移框架、引入云资源或改全局 Agent 配置。

## 可复现入口

先观察一次真实工作流程，确认启动、健康检查、交互、读取状态、清理分别如何完成。复用现有 CLI/连接器；只有重复或脆弱步骤确实需要封装时，才增量建立项目工具。可按实际需要提供：

- `doctor`：依赖、服务/设备连接、目标版本、配置存在性；日志不输出秘密。
- `snapshot`/`inspect`：机器可读的状态、接口、运行信息。
- 项目操作：对应真实用户入口或接口，带明确输入和后置状态。
- `trace`/`measure`：有条件与样本信息的观测。
- `cleanup`：只清理由本次运行创建的资源。

命令有清楚的 `--help`、稳定退出码和可读错误；可破坏操作在可行时提供无副作用的 `--dry-run`。显式报告 dry-run 与实际执行的区别。环境启动成功、操作成功、业务验收成功是不同结论。运行一次成功和有代表性的失败路径后再记录为可靠入口。

## 功能地图

先找项目已有的验证/功能索引；没有且确有复用价值时可建 `docs/verification.md` 作为入口。功能较多才拆为索引与单功能文档，每次只读本任务路径。地图保存能节省重新探索的事实，不复制整份源码或工具帮助。

每个已核实功能记录：

| 字段 | 内容 |
| --- | --- |
| 功能与用户目标 | 使用者最终期待的行为 |
| 入口与前置条件 | UI 路径、接口或命令；账号/数据/硬件/状态要求 |
| 操作与判定 | 可复现步骤及独立预期 |
| 边界和恢复 | 本次发现的失败分支、重试语义、清理方法 |
| 证据与适用版本 | 实际验证命令/记录、源码/协议锚点、核验日期 |
| 尚未核实 | 已知缺口及取得证据的方法 |

先覆盖本次任务与高频路径，范围由需求决定。只有用户要求全量地图时才盘点全部功能，并把已发现但未验证的入口保留为待验证。功能有入口不代表已走通。

## 持久化与更新

硬件配置和接口契约留在项目对应权威文件；地图链接到它们，避免重复副本漂移。记录实际确认的参数和理由，不保存凭证或未经核实的旧聊天猜测。输入版本、命令、环境或行为变化时复测受影响路径，更新“最近验证”信息；维护不能仅润色 Markdown。

共享浏览器/板卡/测试账号/远端范围需明确占用与释放。独立副本只隔离文件；若共享同一外部服务仍会互相干扰。是否使用 worktree、模拟器或云环境按项目条件决定。

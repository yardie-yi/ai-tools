# 21L 调查流程：从覆盖到可证伪的原因链

适用于新问题、全 Boot 或全目录调查。窄问题直接复用已核清单、校时和源码索引，避免反复全量解码。数值、时钟和宏配置以当前版本为准；4101 示例见 [案例笔记](4101-case-notes.md)。

## 1. 固定范围与证据身份

先记录问题原话、日期、电源/显示状态、期望响应、观察窗口及授权限制。区分事故本体、用户提供的参考报告、其他案例和对照窗口。逐条审查参考报告的可验证主张，不能把其结论当原始证据。

输入清单至少包含：原归档路径及 SHA256；解压路径；每个文件的字节数、LF 物理行数、原始首末时间、时间极值、轮转组、完整重复/重叠情况、损坏与解码缺口。原始归档和日志只读，输出放独立目录。复用已有解码器前读实现，记录版本、参数和实际覆盖，不能把选定文件解码说成全部历史 DLT 解码。

必须区别三类去重：

1. 字节完全相同的整个文件：保留两个原件与别名，只选一份进入事件计数。
2. 轮转重叠：保留每个原位置，用可证明的连续记录重叠关系消重；不能按消息文本去掉合法重试。
3. 同一调用的多个输出通道：如 VR 宏与 common_sys 宏相邻打印。关联为同源证据，不能既算两次业务事件又算独立交叉验证。

全目录任务检查全部日志族、无标签行、多行 JSON、同行多个记录头以及无时间的 cache。文件行数、带前缀记录数、业务事件数分别统计。LF 末尾产生的空 split 项不算额外物理行；不要让 `splitlines()` 把其他控制字符也切成源文件行号。

## 2. 逐日志族、逐会话校时

建立校时表：原时钟域、格式函数、日期来源、转换规则、同事件锚点、适用文件/物理范围、未解决冲突。先采用用户明确校准，再用源码与多处锚点检验；若冲突，报告冲突并继续不依赖该配对的工作。

- native 的 `%d`/`%ld tv_usec` 是整数微秒：`.4227` → 4,227 μs → `.004227`；`.51797` → `.051797`。不能当普通十进制小数右补零。
- SDK 固定三位小数若为毫秒，则按毫秒解析；不能套用 native 规则。
- DLT 保留存储头整数秒和整数微秒，再按确认的时区显示；保留 uptime、嵌入日期、解码文本时间。校时前的旧日期不随意改写。
- logger 可能分别调用 `time()` 与 `gettimeofday()`、异步落盘；墙钟回退和跨秒错位必须保留。跨线程打印次序、文件顺序和时间排序分别可追溯。
- 同一 SDK 文件可以由 client/server 或 fork 后不同进程共写，甚至在同一初始化段混用时钟。用同 status/调用序列与原生回调重复锚定，不能按组件名前缀机械分成 UTC/中国时间。
- 没有日期/时区锚的记录，归一时间留空并解释，不用文件 mtime 或编译日期冒充运行日期。

4101 的 native -1h、特定 TTS 启动块 +8h、MD 不偏移和 DLT UTC+8 都是该案已校准范围的规则，不能变成所有 21L 的默认值。

## 3. 划分生命周期与正常基线

为每个实例建立：main/config 初始化边界、原日志 Boot 标记、系统 BootID、uptime、PID/进程角色、线程句柄集合、IG OFF/SHUTDOWN、最后业务记录及下一 main。注明哪个标识来自哪个日志系统，不把 SDK 初始化次数等同系统 Boot 数。

区分：新应用实例、正常关机、带错误的停机过程、整机重新启动、watchdog/崩溃恢复。`Start hmi` 若在 fork/exec 之前只证明走到打印点；PID 采样存在只证明采样时存在；下一实例恢复不能证明旧实例已解锁。

正常对照必须匹配启动年龄、电源阶段、mode、完整负载和版本/配置。分别列出稳定业务窗、停机尾部和无覆盖区；不要让“正常 Boot”标签覆盖整段到下一 main 的空白。正常已完成调用存在选择偏差，不能用它们排除未派发、未进入入口或未完成的故障调用。

## 4. 先协议分层，再关联消息

分别保存并解释：物理链路、逻辑 from/to、外层 opcode、附加信息 ID、文件路径、JSON 内 cmd、payload/序列号、reqKind/mode。先查宏定义与接收分支，再解释数值；同一个 opcode 在另一组 from/to 下可能完全不同。

关联优先级：同实例与同阶段 → 唯一事务 ID/DBus serial → 方向/完整负载/序列 → 路径与业务 cmd → 时间与 FIFO 顺序。没有唯一身份时写“候选关联”，保留未配和多候选，不按最近时间强配。

循环路径如 `RequestN.json`、`Rsp_N.json` 只是文件位置。查清写入者、生成/通知/读取顺序、模 N 复用、覆盖/重入/原子写条件。只有实际读取日志或当时快照才支持内容身份；路径发送日志不证明 JSON 的具体 cmd，也不证明哪个进程写了文件。

## 5. 同时建立事件轴和线程轴

统一事件轴保留原文路径、LF 行号、DLT 解压字节偏移、原始时刻、归一时刻、TID 字段原样、源函数/编译行、payload 及证据等级。再按实例和线程拆出调用子序列。

日志中的 `g_thread_self()` 返回值、pthread_t、Linux TID 和 PID 分列；不把回调指针、SDK appID、cache 数字认作时间或线程身份。不要跨进程用相同数字句柄匹配线程。

同一函数的 start/end 只有在实例、线程、消息身份及执行分支可核对时才构成强配对。逐行查看两个打点包围的代码范围、早退、锁、信号、RPC 和其他工作。标注“handler 观察间隔”“发送前置”“后置日志”等，不以函数名替代实际边界。

## 6. 从代表样本扩展到完整阶段统计

用户只给一段样本时先解释该段；若要判断整个 Boot，就补齐完整 Boot。不要用 15:11 的零回调结论替代其他阶段。

定义统计单位与过滤条件：显式 Request 等待阶段、主类 timeout、显示层 timeout、重试发送、独立 ACK、替代 OK 文本、其他模块 timeout。保留 reqKind 改变、NG 分支、尾部删失、关机和跨层重复。ACK 到达与当前阶段及时成功是不同命题。

全量对照每个阶段的 SDK/语音/业务活动，比较同年龄窗口与暴露时长。INFO/ERR 等级、函数名含 timeout、配置中的 timeout 数值均不直接算业务失败；正返回值不能直接当 errno。

## 7. 追到代码边界，再列候选

追踪 producer → socket → FIFO → consumer → 直接调用/Qt/GObject 信号 → DBus → 第二队列 → 业务文件读取 → ACK。明确每条边的执行线程、是否同步、可能阻塞点、超时配置、返回值是否检查、锁作用域和应答先后。

收到原始包、方法 reply 已提交、队列已投递、业务已消费、JSON 已读、socket 调用返回、对端实际确认是不同节点。不要把 `app_vr_dcu_response` 名称中的 response 当协议 0x290。

依赖生成代码或 SDK 时，区分本机真实源码、DWARF 构建路径、二进制格式串/地址和现场版本。逐条说明可见性；本机 GLib 有源码不表示 AIBS/MD/TTS 内部也有源码。

每个候选写清：已证端点、必要中间条件、竞争解释、正常反例、最小可证伪检查。取消/锁类按 [专项检查](dbus-cancellation.md) 执行。六条 ACK、后台 SDK 活动或单个后置日志都应进入反证，而不是被删掉以维持一个整齐故事。

## 8. 收敛与交付

当可得证据只支持边界时，交付边界和最小补证，不无限重复关键词扫描。区分“缺现场栈/源码所以无法定因”和“权限拒绝/工具错误所以未执行”。报告采用 [证据与修订模板](evidence-templates.md)；既有报告中已经被否定的说法在新复盘明确标为历史，不默默复用。

# 头文件接口补录到飞书

将用户指定头文件的公开接口补齐到指定 Base / Table / View 的功能域分组。新增时，表格中已存在的接口直接忽略：不重复创建、不覆盖、不补写已有行的任何字段；只有用户另外明确要求更新时才修改已有行。此技能不修改源码，也不把头文件中的声明实际编译或调用。

## 输入与工具

从本轮和已确认上下文取得：

- 头文件路径及项目根目录。
- 飞书链接或已确认的 Base、Table、View 标识。
- 目标功能域及用作模板的已有接口行。
- 需要新增、排除或更新的接口范围，以及用户指定的字段规则。

缺少的信息先从上下文、头文件和目标表中解析；只有无法唯一确定时才询问。不要复用其他任务的链接、人员、项目、记录 ID 或“显示/仪表”等分组作为默认值。

飞书操作优先使用 `lark-cli`，调用前读取当前环境的 `lark-base` 技能；认证和权限问题按 `lark-shared` 处理。缺少这些技能时使用 CLI 的 `--help` 确认命令和参数，不猜测写入协议。CLI 不可用时可先完成本地待写入清单，明确尚未写入。

使用用户身份 `--as user`，除非用户指定其他身份。`/base/` 和 BaseApp `/app/` 链接先用 `base +url-resolve` 解析；不要仅凭 `app_` 前缀把 BaseApp 当作妙搭应用调用 `apps +get`。

## 1. 确定表、视图和原始样例

1. 解析链接。用户说“第二个 sheet”时按实际名称查找，确认它是独立数据表还是同表视图，不依赖标签顺序。
2. 读取目标视图配置和字段 schema，确认分组字段、筛选、排序、字段类型及可写性。View 共享底层 Table 记录，新增到表后也可能出现在其他视图。
3. 读取已有接口名、声明、模块/项目等去重所需字段，以及模板行的全部业务字段。指定视图范围用真实 `--view-id`；该视图有筛选时，还要在同表相关模块范围查重，避免把被隐藏的行再次新增。
4. 记录读取优先使用字段投影及 NDJSON 本地文件；以 `has_more=false` 确认查询范围完整。批量读取、视图筛选和分页以当前 `lark-base` 文档为准。
5. 检查用户指定的模板行：接口名、完整声明、参数、说明是否彼此一致。模板业务字段不一致时，识别是否存在不同模块或项目，不任意选第一行覆盖差异。

已有行错位时，报告具体行号/记录、原值和差异。不要把声明列中偶然出现的其他函数名当成该函数已经完整登记，也不要擅自修正已有行。只有当差异影响新增范围时，询问其预期归属；不影响新增的残留错误可保留并单独报告。用户说“我已手动修改”后，刷新有关记录，以最新数据继续，不能仅凭口头确认宣称字段已一致。

## 2. 从头文件提取接口清单

- 阅读头文件及必要的类型定义、相邻注释；不执行头文件中的函数。
- 默认提取 public 方法及导出的自由函数，包含公开静态工厂/释放方法。排除 private/protected 成员、删除的拷贝操作、类型声明、宏和内部实现。构造/析构、操作符、条件编译分支等是否作为契约项，以用户范围和既有表规范为准；明确记录排除理由。
- 保留头文件中的声明原文：返回类型、`static`/`virtual`、指针引用、模板参数、参数名、默认参数、`const`/`noexcept`、`= 0`、分号以及多行声明内部换行。不改成自创的“规范化”签名；可以去掉整条声明外部的缩进。
- 用可靠的解析方式处理多行声明、嵌套括号、函数指针和模板。简单逐行正则只适用于已检查过的简单头文件；提取结果必须与源文件逐项核对，不能以匹配数量代替完整性检查。
- `@brief` 或 `\\brief` 原文放入该接口的示例字段。对明显连续的 register/unregister/get 三件套，可共享其组前 brief，并分别解释注册、注销和读取行为；不要把上一组说明传播到无关函数。
- 没有 brief 的接口明确标记“头文件未提供 brief”，另给基于声明的用途说明，不编造源码注释。

### 已存在接口直接跳过

- 每次新增前读取目标表当前记录建立去重索引，不能只依赖上次任务的缓存、目标视图可见行或用户列出的已录入清单。同一接口即使位于其他分组或被视图筛选隐藏，也视为已存在，不重复新增或移动。
- 在相同模块/类和适用项目范围内，普通非重载接口按函数名匹配，命中即跳过。已有行的说明、参数名、格式或返回类型与头文件不同，不构成另建一行的理由；可以报告差异，但不自动更新。
- 确有重载时，再按参数类型序列和区分重载的成员限定符（如 `const`、引用限定符）辨别。比较时忽略无意义空白、参数变量名和默认值；写入声明仍保留源码原文。不同模块/类的同名函数不应互相抵消。
- 已有行缺少足以区分重载或归属的信息时，列为待确认，不能直接认定不存在后新增。已有重复行保留原样，本任务不清理重复数据。
- 待提交清单自身也要去重；每批成功后将返回的接口加入本次去重索引。重复执行同一补录任务时，已成功新增的接口应全部跳过。
- 所有接口均已存在时，不调用任何写入命令，直接报告“新增 0 条，已存在跳过 N 条”。

## 3. 字段映射

字段名称以目标表 schema 和用户要求为准。以下为常用映射：

| 字段 | 写入内容 |
| --- | --- |
| 接口名 | 只有函数名，不含返回类型、参数或括号；类限定形式遵循用户要求。 |
| 规范接口名 | 头文件中完整声明原文，包括修饰符、参数和末尾分号。 |
| 关键参数 | 最外层参数括号内的原始内容，含类型、引用、参数名、默认值；无参数时沿用表格约定（如“无”），不补造参数。 |
| 简单调用示例 | brief 原文解释，加简短且使用真实接口名的伪代码。 |
| 功能域 | 用户指定分组的现有选项，按 schema 的单/多选结构写入。 |
| 其他业务字段 | 从确认过的同模块模板行沿用，保持空值和已有选项，不根据常识改写接口类型、性质、项目、责任人、状态等。 |

不要复制旧行的系统 ID、自动编号、创建/更新时间、公式、lookup 或只读字段。“变更履历”即使是文本，也属于单条记录历史，不复制旧时间和旧编辑事件到新行；留给系统生成，或仅在任务要求时记录本次真实操作。附件和关联字段按其专用协议处理，不把显示文本直接当 ID 写回。

示例要足以表达如何调用，但不能暗示已编译或测试。根据头文件约束说明回调线程、阻塞读取、对象释放及输入范围；未知枚举或协议值用明确的伪代码占位，不猜数字。注册示例中的回调不安排日志、UI、阻塞调用或耗时业务，除非源码明确允许。无阻塞的队列也应说明容量/失败处理，引用参数需复制后再跨线程使用。具体写法见 [references/examples.md](references/examples.md)。

## 4. 准备并提交新增记录

1. 形成本地接口清单和待写入 JSON，保留来源头文件、目标坐标、模板记录、排除项和查重结果。区分新增、已存在跳过、冲突；待写入 JSON 只包含确认缺失的接口，不把已存在项混入创建或更新请求。
2. 校验每条记录：声明和参数与源码一致；brief 对应正确；功能域符合目标；其他字段与模板一致；无漏项和重复签名；字段类型及选项合法。
3. 按头文件顺序提交缺失项。设置分组字段可让新行进入相应分组；视图有排序时显示位置由视图决定。用户要求“往下新增”时不要擅自更改视图排序或移动旧记录，也不要承诺 CLI 无法控制的精确插入位置。
4. 已明确要求补录即授权新增，不为普通新增重复索取批准。目标存在影响结果的歧义时才暂停相关写入；写入前可用 `--dry-run` 检查目标和 payload。
5. 使用当前 CLI 支持的 `@file` 或结构化参数提交 JSON，避免 shell 转义损坏中文、模板尖括号、引用及换行。CLI 文件参数若要求相对路径，就在暂存目录中执行；不要把绝对路径硬传给该参数。
6. `base +record-batch-create` 按 CLI 上限分批（当前最多 200 条），同表串行写入。成功用 `ok=true` 或退出码 0 判断，保存返回的记录 ID 和每批结果。
7. 失败或超时不立即重发。先确认该批是否已写入，只重试确实缺失的记录；无法确定结果时停止追加并报告。权限失败不切换身份、不扩大权限或另找写入口绕过。

## 5. 回读核验与交付

全部批次结束后按返回的记录 ID 定向回读，一次核验新增行的四个内容字段、功能域和继承业务字段。考虑服务端短暂延迟，可以有限重读；不要因暂时查不到而重新创建。若任务要求原行保持不变，只对比相关原行，不无端重复读取整库。

核验总数与源清单对应：源接口 = 已有有效接口 + 本次新增 + 明确排除/待处理项。若有冲突或漏项，明确报告，不宣称完全同步。

最终简洁给出目标视图链接、新增数量、已存在跳过数量和核验结果；只有另获更新授权时才报告更新数量。若有残留旧行不一致、未提供 brief 或写入失败，仅报告实际限制；不要把“已生成 payload”说成“已写入”。不主动再读取用户刚手动修改的内容，除非它影响尚未完成的任务或用户要求验证。
